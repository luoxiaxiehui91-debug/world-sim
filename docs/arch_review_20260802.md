## 关键决策（五条铁律）

1. **天璇 P0 hotfix 与 B+A/NOVEL 重写是两件独立任务**，严禁捆绑。`run.py` 补写 `predictions` 表，工期上限 2 天，五颗星价值链的单一断路点必须立即处理。

2. **玉衡不独立成星**。`weight_matrix.py` 并入天玑 V2 目录；评分→校准报告→权重写回三步保留独立函数+独立日志，`weight_update_log` 保留为独立审计表，支持写回失败时单步重试。

3. **瑶光和天权永久关闭独立立项**：瑶光降级为天枢 `observability.py` 三数字 ntfy 子任务（2 小时），天权降级为 `causal_assumptions.md` 运维文档（1 天），两者的价值在现有架构中已被完全覆盖。

4. **天玑代码物理可驻留天枢目录**（单人项目 import 守卫+目录级 README 优于物理分离），但天玑纯验证层的职责边界须通过代码守卫而非目录位置来执行。

5. **开阳 v1.7.0 立即部署，A3a 控制 API 永久 MOCK 并在 UI 显式标注**。静默 MOCK 是架构诚信问题，不允许以任何形式对外演示为已完成功能。

### 二、天璇（macro-sim）⭐ P0 · 待部署（P0 hotfix 待执行）

| 项 | 内容 |
|---|---|
| **定义** | 月步长 Monte Carlo 仿真引擎，唯一职责是产出 Brier 可计算的概率分布预测并持久化写入 predictions 表 |
| **职责** | ① 消费 sim_trigger.json 触发后运行 Monte Carlo（12 Agent × 100 次，月步长）<br>② **将每个预测变量的概率分布（非点估计）持久化写入 predictions 表**（P0 hotfix 目标）<br>③ 产出供人阅读的仿真报告<br>④ B+A/NOVEL 完整重写（Sprint 1-3，提升仿真质量，与 hotfix 解耦） |
| **输入** | grv_latest.json（天枢契约文件，只读）；sim_trigger.json（天枢触发信号） |
| **输出** | predictions 表（概率分布格式，含变量名/预测时间窗口/分布参数，天玑唯一消费方）；仿真报告（开阳展示用） |
| **边界约束** | 不读 grv_weights.yaml，不调用天玑/玉衡任何函数。与天玑的唯一接口是 predictions 表结构契约。**P0 hotfix（run.py 补写入，2 天）与 B+A/NOVEL 重写（3-5 周）严禁捆绑排期。** hotfix 写入格式必须是概率分布，每个预测变量的 ground truth 观测逻辑须在 hotfix 设计阶段书面定义。 |
| **当前状态** | P0 inode 断链待 force-recreate 部署。predictions 表仅 1 条测试数据，run.py 只写报告不写 predictions，整条校准链在数据层完全断路且已持续数月无告警捕获。 |

> **⚠️ P0 说明**：predictions 表写入缺失不是架构缺陷，是遗漏的一组函数调用。hotfix 工期 1-2 天，可在 Sprint-0 当前阶段立即执行，不等 B+A/NOVEL 重写。

### 三、天玑（macro-ji）⭐ P1 · 部分实现（代码在天枢目录）

| 项 | 内容 |
|---|---|
| **定义** | 纯验证层：消费天璇预测，计算 Brier 评分，产出月度校准报告，V2 触发权重写回 |
| **职责** | **V1**：读取到期 predictions，与 ground truth 对比，计算 Brier 评分和校准曲线；产出月度校准报告（样本量 ≤ 5 时必须显式标注置信区间过宽，禁止给出伪精确结论）<br>**V2**：合并玉衡 weight_matrix.py 后，在阈值满足时以独立函数调用触发权重写回（三步：评分→报告→写回，各自独立函数+独立日志） |
| **输入** | predictions 表（天璇写入，只读） |
| **输出** | 月度校准报告；V2 新增：weight_update_log（独立日志表）；V2 新增：grv_weights.yaml 更新指令（通过 weight_matrix 模块触发） |
| **边界约束** | 不承担任何推演职责，不生成预测，不调用天枢 fetcher。代码物理驻留天枢目录须加目录级 README 和 import 守卫。2026-09-30 门控是条件门控（前提：天璇 P0 修复后首批真实 predictions 落表），当前前提未满足，不得作为固定里程碑规划。 |
| **当前状态** | tianji_verifier.py 和 tianji_db.py 已存在但从未对真实预测运行过。predictions 表仅 1 条测试数据。weight_update_log 永远 0 行。tianji_db.py 中存在两张归属不明的表（narrative_chunks/narrative_density_flags），须在 Sprint-1 前澄清归属。 |

> **天玑争议裁定**："天玑是验证层还是推演层" → **裁定为纯验证层**。代码证据：tianji_verifier.py 只做月度评分，没有任何推演逻辑。推演是天璇的职责。"天玑是否应兼并权重反馈"→**裁定为 V2 时兼并**（V1 只做评分，V2 合并玉衡），样本量极少时权重更新无统计意义。

### 最有价值的观点

**怀疑者（第二轮）**：predictions 表断路存在数月说明的不是推送格式不对，而是 owner 根本没有把"predictions 表是否有新行"纳入任何健康检查逻辑。SRE 混淆了"观测渠道"和"观测指标覆盖"两个不同的问题。

**数据科学家（第二轮）**：P0 修复不是"让天璇写 predictions"，而是"让天璇以 Brier 可计算的概率分布格式写 predictions，并同步定义每个预测变量的 outcome 观测逻辑"。两者缺一，校准链依然是空管。

**SRE（第二轮）**：当天玑同时承担"评分"和"权重写回"两件事时，一个 Brier 评分逻辑里的 bug 不再只产生"报告数字偏了"这种可见故障——它会直接静默地改写 grv_weights.yaml。纯验证层的最坏失败模式是"评分结果不准确，但原始数据不被污染"；混合层的最坏失败模式是"权重被静默腐化，下游所有 GRV 计算都在错误基础上运行，但系统看起来完全正常"。

**用户代理（第二轮）**：正确的数据流应该是：天玑把校准结果写入 weight_update_log 表；天枢的月度调度任务读取这个表，由天枢自己决定是否执行权重写回。天玑只有读权限（读 predictions 表）和写自己 output 的权限，没有写 grv_weights.yaml 的权限。这样学习闭环完整，同时天枢对自身状态保持唯一写权威。

**产品经理（第二轮）**：天玑 V1 的合法职责是纯验证层（Brier 评分 + 校准曲线），权重反馈作为天玑 V2 在首批评分数据积累后触发。把权重反馈硬塞进 V1 里，结果要么让 Sept 2026 的 milestone 延期，要么让权重更新在样本量极少时就跑，产生比人工拍定更差的权重。
