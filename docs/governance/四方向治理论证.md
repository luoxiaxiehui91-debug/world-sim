## 2. 四方向论证（全部 verdict: pass）

### 方向 A：单一真源制度 + 记忆降级（架构师）

**核心设计——单一真源仲裁优先级表：**

| 序 | 冲突 | 裁决 | 依据 |
|---|------|------|------|
| 1 | 文档/记忆 vs 运行态 | 运行态赢，文档判过期→降级 | 案例1/2/3/8 |
| 2 | 运行态 vs 代码真源 | 判「部署漂移事件」，走 D 收敛 | 案例4/7 |
| 3 | 天枢 repo vs 运行区 | 运行区（热挂载）赢，repo 为归档 | 改 py 即生效 |
| 4 | 天璇 repo vs 宿主运行区 | repo/容器赢，宿主运行区为僵尸副本 | COPY 模式 |
| 5 | 开阳 源码 commit vs dist | dist（运行态）赢，判「部署超前」 | 案例3 CHANGELOG 超前 |
| 6 | 数据文件 | 容器内 inode 一致为准 | 天璇/天玑共享同 inode |
| 7 | 计数类 | ast 权威解析为准，禁 grep 缩进正则 | 案例6 |
| 8 | SMB | 永不参与仲裁（读亦不可信） | 案例8 |

**可执行决策树**：① 定位真相树（天枢运行区 / 天璇容器 / 开阳 dist）→ ② 判对象类型（代码/数据/计数/状态）→ ③ 代码按上表 3/4/5 行取真源；数据/计数/状态一律 docker exec 容器内跑 Confirmation 命令 → ④ 冲突按上表 1/2 行裁决，产出两类事件：「文档过期」或「部署漂移」，各自有处置通道（前者触发记忆降级，后者交 D）。

**记忆降级规则：**

| 层 | 触发条件 | 降级动作 | 执行者 |
|----|----------|----------|--------|
| T1（设计权威） | 被 Confirmation 证伪 / 被新 ADR 取代 | 标 superseded 指向新真源，降为「历史记录」 | 负责人人工走 PR，AI 仅起草 diff |
| T2（实时状态） | TTL 7 天未复验 / 任一验证命令失败 | 标 as-of 日期移入流水，降为「历史快照」 | AI 自动执行 |
| T3（append-only） | 历史被证伪 | 追加「更正」条目（不删不改） | AI 执行 |
| MEMORY.md | 红线永不降级；硬事实被证伪 | AI 修订 + 负责人复核，留更正记录 | AI + 负责人 |

**可行性**：高。不重构系统，只定仲裁规则 + 收敛验证命令；四容器真相树已识别，ast/容器内执行基础已具备。成本 = verify.sh + 真源注册表 + T1/T2 迁移脚本，均为小工程量。

**依赖关系**：
- **C 依赖 A**：A 产出的注册表（对象→位置→命令）即 C 的验证清单，顺序 A→C，A 不落 C 悬空。
- **A↔D 相互强化**：A 定义「D 收敛后哪条通道是真源」（COPY 收敛后以 repo 为准）；D 收敛后 A 仲裁表 3/4/5 行可简化为单通道。并行推进，但 D 收敛方向需以 A 仲裁表为输入。
- **A 与 B 互补无冲突**：B 分治文档类型 = A「文档只引用不复制」的落地；A 定「哪类文档可写数字」，B 执行分治。

**优先级**：A 核心（注册表 + 仲裁规则）= **P0**（8 案例根因且阻塞 C）；记忆降级 = **P1**（防御层，依赖 A 命令设施）。

**最大风险 + 防线：**
1. 注册表自沦为第二套文档 → 注册表走 PR 治理；文档/记忆裸数字由 B 分治 + C 验证命令拦截。
2. 验证命令在错误环境执行（SMB 幻影误判）→ 硬规则「NAS 仅 SSH + docker exec」，verify.sh 强制容器内执行域。
3. 仲裁被误用（热挂载/COPY 混淆、僵尸副本误当真源）→ 决策树强制先「定位真相树」，注册表每条记录标注真相树归属。

**总评**：先定位真相树、再按对象类型仲裁、命令即契约，把数字收口到真源注册表一处，配合 T1/T2/T3 分层降级，是成本最低且可验证的根因治理。

### 方向 B：文档类型分治（PM）

**核心设计——分类判定规则（一眼三问）：**
- a) 时间轴：描述「过去已发生」→ 实录类；描述「未来要做」→ 意图类
- b) 动词：含「已/完成/部署/上线」→ 实录；含「将/计划/拟/待」→ 意图
- c) 可验证性：能绑定 commit hash + 验证命令 → 实录；不能 → 意图

**落地要点：**
1. 物理分治：`docs/records`（实录）与 `docs/plans`（意图）分目录，文件头强制声明类别 + 最后核对时间
2. 实录硬约束：每条 CHANGELOG 绑定 hash + 验证命令，写后立即执行验证，通过才合入
3. 意图软约束：必须带状态标记（未实施/进行中/已实施），标「已实施」必须反向链回实录条目
4. 单向状态机：意图→实施→实录，杜绝「预告片当实况」
5. 验证命令模板化：每服务提供 verification 脚本，条目格式化为可执行 check
6. AI 记忆接入：AI 按类型模板生成文档，记忆读取以实录类 + 验证结果为准
7. 存量改造：CHANGELOG/operations 归实录类；ROADMAP/design/decisions 中带「待实施」的归意图类并补状态标记

**可行性**：中高。纯制度 + 模板改造，不依赖新工具、成本低；但依赖人工纪律持续执行，存量重分类是一次性工作量。

**依赖关系**：B 是 A 的执行层——A 定义「什么是真相」（以仓库/运行态为准），B 保证文档如实反映真相；B 的验证需要 A 提供锚点（commit、实测输出）。二者互补不冲突。

**优先级**：**P0**。8 个漂移案例多数是「文档≠事实」，B 直接打击最大病灶「文档是宣言不是实录」，成本最低、见效最快，且是其他方向的共同基础设施。

**最大风险 + 防线：**
1. 人工惰性使意图类悄悄变成「未验证实录」→ 文件头声明 + review 兜底
2. 验证脚本自身漂移，产生「验证通过但实际未发生」的新谎言 → 验证脚本从单一真源锁定
3. 存量重分类激进丢历史 → 归档保留而非物理删除

**总评**：用「过去可验证、未来可标注」的二分法把文档从叙事变成可审计的账本，是四方向中成本最低、直击病根的止血方案。

### 方向 C：Confirmation 验证机制（QA）

**核心设计（10 条）：**
1. 建「验证命令注册表」：每真源一行，字段 = 对象/命令/期望值/实测值/口径版本/负责人/上次运行/命令哈希
2. 命令必须可复制实跑；入表前必须真跑通过，禁伪命令（今日已现虚构 weight_health job）
3. 命令从真源提取而非文档手写——GRV 键数命令由 schema 生成，保证同源
4. 注册表本身纳入版本库，做格式/哈希自校验，防篡改
5. 期望值取自 Spec/代码常量，非实现返回值，杜绝「同义验证」绿但零信息
6. 命令与对象版本绑定（schema v2→命令 v2），失效时显式标记，禁静默失败
7. 扩展 ADR Confirmation 而非新建：把「每条 ADR 一命令」推广为「每条真源一命令」
8. 触发：变更后必跑（diff 触发）+ 每周巡检全量 + 关键命令进部署门禁（开阳 D3 一致性）
9. 巡检产出「验证报告」入 operations，「声称 vs 实测」差距自动转缺陷单
10. devops 维护注册表，QA 随机抽测实跑审计命令真实性

**可行性**：高。成本极低（每命令一行 shell/python），直接命中共同根因「验证缺失」，且有 ADR 先例复用。

**依赖关系**：
- 依赖 A（单一真源）：先定「哪个是真源」才能绑命令，无真源则命令无处可绑
- 依赖 D 收敛部署通道（案例4），命令须基于唯一通道
- 与 B 互补：命令是流程的量化检测器

**优先级**：**P0**。8 案例全是「声称 vs 实测」差距，验证命令是最低成本的直接止血；无验证则任何真源定义都无法证明生效。

**最大风险 + 防线：**
1. 命令失真/被伪造 → 命令必须从真源代码提取（非手写）+ 注册表哈希 + QA 抽测 +「无输出即失败」
2. 命令过期失效（路径/镜像版本变）→ 版本绑定 + 失效显式标记 + 变更必跑及时更新
3. 验证弱化为「为绿而绿」（弱化期望/只跑不判）→ 期望值独立于实现，gap 自动转缺陷单，不人工判

**总评**：方向 C 用最低成本把「声称」变成「可证」，是 8 个漂移案例的共同解药；但「验证命令本身」必须当作被测对象纳入反作弊审查，否则验证体系会重演今日之病。

### 方向 D：部署通道收敛（DevOps）

**核心设计——每子系统钉死单通道（决策表）：**

| 子系统 | 唯一通道 | 授权 | 部署前验证 | 部署后验证 |
|--------|----------|------|------------|------------|
| 天枢 | SSH 直改运行区 py；scheduler.py 改后 docker restart | 开发者 + 变更记录 | compileall + import smoke | DATA_DIR==/workspace/data 断言 |
| 天璇 | deploy.sh 仓库直构（运行区归档） | lead | 仓库 sha256 基线 + 构建成功 | 容器 image ID==构建 ID + health |
| 天玑 | 仓库 build macro-tianji → compose up | lead | 构建成功 | 容器运行 + health |
| 开阳 | scp dist → chmod -R a+rX → docker restart（只覆盖不清理） | lead | 本地 build（禁 SMB 构建） | HTTP 200 + index.html 引用 bundle 存在 |

**通用红线**：禁 mv 原目录（断链）；一切 NAS 操作走 SSH 禁 SMB；rsync 整目录仅 lead；部署后强制校验，不符即回滚。

**可行性**：高。四容器各有已运行通道，收敛是「钉死 + 校验门禁」而非新建；天璇仓库直构已被天玑验证。

**依赖关系**：
- A 仲裁表 3/4/5 行（运行态 vs 代码真源冲突、双通道分叉、漂移定位）收敛后可合并为一行「漂移=未走唯一通道，判违规回滚」，无需逐案仲裁
- C 验证命令绑定 channel 来源，只认唯一通道产出的状态断言——C 为 D 把关，D 为 C 提供可验证的通道事实

**优先级**：**P0** 天璇双通道收敛（rsync --delete 事故两次 + deploy.sh 与实际不符）；P1 全子系统决策表落地 + 部署后校验门禁；P2 CHANGELOG 与实测对齐（根除案例7 假声称）+ 运行区归档。

**最大风险 + 防线：**
1. 收敛期误动运行区致无法回滚 → 先冻结 .archive + 只读，留 7 天回滚窗口
2. 仓库与运行区 env/compose 有差异 → 迁移前 diff，以实际运行配置为基线补仓库
3. 唯一通道被手工绕过成新漂移源 → 部署后 image ID/DATA_DIR 断言 + C 门禁，绕过即事件

**总评**：D 收敛 = 每子系统钉死一条通道 + 部署后强制校验，让「声称」永远等于「实测」，把漂移从仲裁问题变成可自动判定事件。

## 3. 交叉一致性检查（团队 lead 执行，无冲突）

| 检查项 | 结论 |
|--------|------|
| A↔C | C 依赖 A：注册表即验证清单，A 不落 C 悬空 → 顺序 A→C |
| A↔D | 相互强化：D 收敛后 A 仲裁表 3/4/5 行简化为一行「漂移=未走唯一通道」；D 收敛方向以 A 仲裁表为输入 |
| B↔C | B 实录硬约束（绑定 hash+验证命令）引用的正是 C 注册表；B 的验证脚本须从单一真源锁定 |
| D↔C | C 验证命令绑定 channel 来源，未标注通道即不通过；D 为 C 提供可验证的通道事实 |
| D 建议 | 「漂移=未走唯一通道」写入 A 仲裁表作为统一判定，取代逐案仲裁（已采纳并入 A 表第 2 行） |

## 4. 落地顺序建议

1. **A 注册表 + C 验证命令** 同步启动（A 先定真源归属，C 立即挂命令）
2. **D 天璇双通道收敛** 并行（rsync --delete 两次事故是最高危项）
3. **B 文档分治** 随行（存量重分类 + 文件头声明，一次性工作量）
4. **记忆降级规则**（T1 人工 PR / T2 自动 stale / T3 只追加更正）作为防御层紧随其后

**依赖链**：A（注册表）→ C（命令）→ D（通道）→ B（文档），其中 A 与 D 可并行启动。

---

## 5. 一句话总评

> A 定真相、B 管文档、C 证声称、D 收通道——四者咬合成一条闭环：**文档只引用不复制 → 命令从真源提取 → 期望值独立于实现 → 通道唯一可回滚**。QA 的提醒值得单独强调：验证命令本身必须当作被测对象纳入反作弊审查（QA 抽测 + 注册表哈希 + 无输出即失败），否则验证体系会重演今日之病。
