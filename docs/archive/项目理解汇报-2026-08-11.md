## 一、STATUS.md 是什么？

**是入口 / 交接文档，不是代码入口。** 它自己定义的就是"新 session 冷启动第一入口"和"实时交接文件"。作用：
- 锁死项目位置（工作区 vs NAS repo vs SMB 挂载的三角关系）
- 锁死四容器、当前主线、R4 红线、已知坑
- 给未来接手的人或 AI session 当"防迷路"起点

它不指向任何可运行代码——真实代码在 NAS 容器里跑。

## 四、⚠ 关键理解风险（你最担心的"偏移"）——已亲自核实

**核心事实：这个 WorkBuddy 工作区是一份落后于线上系统的"文档/设计镜像"，不是可运行真相。** 全部代码在 NAS 容器 + GitHub repo。

亲自核实的矛盾点：
- **开阳副本 = v1.7.0（2026-08-02）**，STATUS/ROADMAP 声称线上 v1.10.8。工作区开阳缺报告中心、FCI/GSCPI 面板、风险面板、news_geo 同地点聚合等全部 v1.10.x 特性（路径：`世界推演系统开阳/kaiyang-wave2/`，VERSION=1.7.0）。
- **天璇工作区目录为空**（仅 `.workbuddy/`），代码只在 NAS 容器。
- **天枢工作区只有 design/ + compute_probit.py + 少量脚本**；真实的 scheduler.py / compute_fci.py / geo_risk_vector.py / weight_matrix.py / tianji_db.py / slow_variables.py / news_exporter.py / fetch_*.py **均不在工作区**。
- crucix 论证文档（arg-round1/arg-map/crucix-dependency-analysis）**不在工作区**，仅被项目导航引用（在 NAS repo `macro-scan/docs/`）。
- 所有部署脚本（docker-compose/deploy.sh/entrypoint.sh/nginx conf）**均不在本地**，只有描述它们的文档。

STATUS 文档内部的自我矛盾（agent 发现，需 `ssh nas` 终裁）：
- crucix "退场中" vs STATUS 自述"实测仍活跃独立运行 30/30"——措辞与运行事实不一致。
- 仓库 `docker-compose.yml` 只映射 8899，运行区实为 8899+8900——照仓库部署会丢控制 API。
- 静态闸 `static_gate_check.py` 被证是"稻草人"（扫不存在的目录、未接 pre-commit）。
- 版本号三处不一致（3.8.12 / 3.8.7 / v3.8.11）。

## 六、给主理人的结论

1. STATUS.md 确实是合格的交接/入口文档，信息密度高、主线清晰。
2. 但**不要把工作区里的代码副本当成真相**——它整体滞后且残缺（尤其开阳落后 3+ 版本、天璇空、天枢只有设计稿）。任何诊断/改码必须走 `ssh nas` + `docker exec`。
3. 系统本身健康度尚可：R4 校准已收编、crucix 退场实施闭合待观察窗、开阳线上已大规模补全。真正阻塞项是 silence 治理挂起 + 几处 P0 未修（sim_log.db、时区）。
