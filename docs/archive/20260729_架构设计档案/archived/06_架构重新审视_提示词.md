## 0. 你在做什么

你接手**世界推演系统**的架构设计会话。当前系统有两层已运行（天枢观测 v3.6.5、天璇仿真 v2.0.13）、一层仅存草稿（天玑验证 v0.1），运行在个人 NAS 上。

**北斗七星框架**是规划工具，不是硬性指标：
- 🚫 **不是**要求你填满 7 层——3 层、4 层、5 层都可以

北斗七星由**斗**（勺体四星）和**柄**（勺柄三星）组成，恰好提供了一个"核心处理链 + 输出反馈链"的二分框架，但不强制每颗星都对应一层。

## 3. 数据源扩充后暴露的结构性张力（7 层框架试图解决什么问题）

### 3.1 存在但割裂

```
天枢 → 天璇：有接口，但单向。天枢膨胀了（22源,11维），天璇还在消费旧契约（5+1维）
天璇 → 天枢：零反馈。天璇推演完，天枢不知道、不引用、不学习
天玑 → 天枢/天璇：不存在
```

### 3.2 缺失但需要

```
知识层：因果链"油价↑→通胀↑→美联储加息"是硬编码在 LLM prompt 里的，不是系统自己维护的
情景层：`run_macro_analysis.py --event "台海危机"` 可以用，但没有系统化的情景管理
交互层：天枢有 WebUI，天璇有 ntfy 推送，但它们是两个独立入口，没有统一的"世界状态仪表板"
进化层：22 个数据源、11 维权重、10 条共振规则——全凭人工经验调，系统从不自我质疑
```

### 3.3 Crucix：系统里的"第四维"

当前架构有一个容易被忽略的组件——**Crucix**：

```
天枢 (macro-scan)           Crucix (:3117)          天璇 (macro-sim)
┌──────────────┐           ┌──────────────┐         ┌──────────────┐
│ 22类数据源    │           │ 独立情报终端   │         │ 12 Agent MC │
│ GRV 11维     │──JSON──▶ │ gscpi/nuke    │         │ 概率路径树   │
│ LLM分析       │ 8s timeout│ sdr/air信号   │         │              │
│ signal_synth │◀─────────│ EIA/FIRMS内部 │         │              │
│              │  注入prompt│ ACLED(已放弃) │         │              │
└──────────────┘           └──────────────┘         └──────────────┘
```

**Crucix 是什么**：独立容器，自建无外部限速，实时多源情报。每次 `run_macro_analysis.py` 调用 `/api/data`（8s timeout），将信号注入 LLM prompt。

**当前定位的模糊性**：
- 它既不是天枢的子模块（独立容器），也不是独立的一层（只被天枢消费）
- 它内部已经有自己的数据源（EIA/FIRMS），和天枢的 fetcher 有**职责重叠**——天枢的 `fetch_energy_eia.py` 和 Crucix 内部的 EIA 采集在做同样的事
- ACLED 在 Crucix 内已放弃（需 edu 邮箱），但天枢没有这个信息——两个系统的能力矩阵从未同步
- CUCI-1~5 五轮迭代完成了数据注入→LLM prompt 的链路，但它始终是"天枢调用的外部服务"而非"系统架构中的一层"

**信息源扩充后的新问题**：
- 天枢现在有 22 个数据源，其中 9 个孤儿源（BDI/FAO/航班/商品/中观/加密冗余/新闻/HDX/EIA）——这些是否应该转进 Crucix 作为统一情报平台？
- 还是反过来，Crucix 的信号（gscpi/nuke/sdr/air）应该被天枢的 fetcher 直接拉取，取消 Crucix 这个独立服务？
- 或者两者并存，明确分工：天枢管"结构化时序"，Crucix 管"非结构化信号"？

**核心抉择**：

| 方案 | 思路 | 优点 | 风险 |
|---|---|---|---|
| A. 吸收 Crucix | 把 Crucix 的信号采集纳入天枢 fetcher，关掉 Crucix 容器 | 减一层维护、统一调度 | 天枢 fetcher 已有 22 个，再加会膨胀 |
| B. 扩展 Crucix | 把 9 个孤儿源转进 Crucix，让它成为"统一情报平台"，天枢只消费 | 职责清晰（天枢=推演，Crucix=情报） | Crucix 是否设计来承载这些源？技术债未知 |
| C. 维持现状 | 天枢管采集+推演，Crucix 管实时信号补充 | 无迁移成本 | 两个系统各自膨胀、职责重叠加重 |
| D. 重新定义 | 把 Crucix 定位为北斗七星中的一层（比如天权-知识层的信号源） | 架构上有正式名分 | 可能过度设计 |

**你的任务**：在思考整体架构时，给 Crucix 一个明确的定位——是留、是砍、是扩、还是重定义？

### 3.4 7 层的风险

- **复杂度爆炸**：当前两层已需要独立部署和运维，7 层会成倍放大
- **层间接口膨胀**：每两层之间的契约都需要维护和版本管理
- **过度抽象**：不是每个系统都需要"知识层"和"进化层"——可能一个模块就够了
- **维护负担**：个人项目，7 层的文档、测试、部署脚本都会是负担

**你的任务之一就是判断：哪些层值得独立、哪些应该合并、哪些只是远期愿景。**

## 4. 设计问题（逐层递进）

### 第一组：分层原则

**Q1. 有必要 7 层吗？**

当前实际在跑的只有 2 层（天枢 + 天璇），天玑有草稿。从 2 层一步跳到 7 层，中间是否有更合理的 3-5 层方案？

比如：
- **3 层**：天枢(观测) → 天璇(推演+验证) → 开阳(交互)
- **4 层**：天枢(观测) → 天璇(推演) → 天玑(验证) → 开阳(交互)
- **5 层**：天枢(观测) → 天权(知识融合) → 天璇(推演) → 天玑(验证) → 开阳(交互)

你推荐几层？为什么？

**Q2. 斗（天枢/天璇/天玑/天权）和柄（玉衡/开阳/摇光）的分界线合理吗？**

斗 = 数据流入 → 处理 → 内化；柄 = 消费 → 交互 → 自省。这个二分法是否自然？天玑（验证）放在斗里还是柄里更合理？

**Q3. 哪些层可以共用基础设施，不需要独立容器？**

当前天枢和天璇是两个独立 Docker 容器，各自有 LLM 调用链。如果扩展到 7 层，每层都要独立容器吗？还是"逻辑分层、物理合署"？

### 第二组：Crucix 的位置 — 留、砍、扩、还是重定义？

**Q4. Crucix 应该是独立的一层吗？**

当前 Crucix 是一个独立容器，但不在任何架构定义中——它是"天枢的外部依赖"，不是"系统的一层"。在北斗七星框架里：
- 它是否可以映射到**天权（知识层）**？——作为结构化和非结构化信号的融合点
- 它是否可以吸收**天枢的 9 个孤儿源**？——让天枢专注 GRV 核心维度，Crucix 成为统一情报平台
- 还是反过来——**砍掉 Crucix**，把它内部的信号采集纳入天枢的 fetcher 体系（用 fetcher_base 统一管理）？

**Q5. 天枢和 Crucix 的职责重叠怎么解决？**

当前 EIA 能源数据在两个地方被采集：
- 天枢的 `fetch_energy_eia.py` → 落盘 `data/energy_eia.json`
- Crucix 内部的 EIA 采集 → 注入 LLM prompt

这种双重采集是浪费，还是合理冗余？信息源扩充后（22 类），如何避免更多这种重叠？有没有一个原则来划分"什么归天枢采集、什么归 Crucix 采集"？

**Q6. 更多信息源转进 Crucix 的决策标准是什么？**

如果走"扩展 Crucix"路线，哪些源该转进去？
- 实时/高频信号（地震、航班、加密）→ 适合 Crucix 的流式架构？
- 结构化时序（FRED、汇率）→ 应该留在天枢？
- 月频源（FAO、中观）→ 两边都不急？

请给出一个**分类标准**——不是简单列举，而是定义"什么样的源适合放在哪里"的决策规则。

### 第三组：各层职责边界

**Q7. 天权（知识层）和天枢（观测层）的边界在哪里？**

天枢已经在做：ChromaDB 向量库（558 个 .md，4156 块）、知识库更新、RAG 检索。这和"知识层"有什么不同？天权是应该接管天枢现有的知识库能力，还是做天枢不做的事（比如因果链建模、跨域知识图谱）？

**Q8. 玉衡（情景层）和天璇（推演层）的区别是什么？**

天璇 already does "GRV 告警 → Monte Carlo → 概率路径树"。玉衡应该做天璇不做的什么？
- 离线 What-if（不依赖实时 GRV 告警）？
- 多维情景组合（sanctions_risk=80 AND earthquake_risk=100）？
- 长时间尺度推演（天璇是 24 个月，玉衡可以做 10 年）？

**Q9. 开阳（交互层）需要统一什么？**

- 天枢日报 → ntfy 推送（手机）

- 天璇仿真报告 → ntfy 推送（手机）

**Q10. 摇光（进化层）是真实需求还是哲学占位？**

"系统自省"听起来很美，但具体做什么？

在当前"无 ground truth"约束下，哪些自省是**可操作的**、哪些是**纯哲学**？

## 5. 北斗命名的使用原则

北斗七星在中国文化中有"定方向、辨四季"的含义——《鹖冠子》："斗柄东指，天下皆春"。这个意象与"世界推演系统"的定位契合。

**使用原则**（非硬性约束）：
- 已有运行层的北斗名（天枢/天璇）保留，已有草稿的（天玑）可沿用
- 新增层有自然对应的才用北斗名，不强行凑数
- 最终方案不需要是 7 层——3、4、5 层都可以，空着的星就是"远期预留"
- 命名只是锦上添花，架构设计本身才是核心

## 7. 关键提醒

- **信息源扩充后重新审视系统是这次设计的核心动机**——北斗七星只是辅助思考的框架，不是目标。如果最终方案是 3 层或 4 层，完全合理。
- **北斗七星是灵感，不是枷锁**——如果某颗星找不到自然对应的层，宁可标注"远期预留"也不要生造功能塞进去。
- **复杂度是债务**——每多一层，就多一份维护成本。只为"明确解决问题"的事加层。个人项目的架构应该像瑞士军刀，不是航母战斗群——功能齐全但每个都简单够用。
- **从整体出发，不看某一层**——天枢内部的问题可能在天璇或天权层面更容易解决。不要在单一层面死磕。
- **先分边界，再填内容**——层的职责边界（谁做什么、不做什么）比内部实现细节重要 10 倍。
- **一次一个维度**——不要同时回答所有问题。从 Q1（层数判断）开始，达成共识后再往下推。
