# 07 北斗七星架构重设计（最终方案）

> 日期：2026-07-29  
> 作者：高见远（software-architect）  
> 上下文：数据源扩至 22 类、GRV 扩至 11 维后，原 7 层框架已显见结构性不匹配。本次重审据此做出**最终方案**，不留模糊空间。  
> 关联阅读：`01_事实地基.md`、`00_终裁_架构演进优先级.md`、`S:\world-sim\docs\overview.md`、`S:\world-sim\docs\discussion\北斗七星架构_深度评估_20260729.md`

## 0. TL;DR — 一句话答案

**5 主层 + 2 横切 = 逻辑 7 层、物理 4 容器：**

```
天枢（观测）→ 天璇（仿真）→ 天玑（验证）──┐
   ↑                                       │
   └───── 玉衡（反向校准通道）──────────────┘
                                            ↓
                                         开阳（呈现/发布）
                                            ↑
[横切] Crucix（实时信号总线） 注入 → 天枢 LLM 链路
[横切] 摇光（自主运维/SRE） 监控 → 全层
```

**Crucix 定性：D（重定义为"实时信号总线"）**——既不吸收、也不扩张为门户，更不维持模糊现状，而是明确划清"结构化时序归天枢、非结构化实时信号归 Crucix"的边界。

**关键修正：**
- 砍"天权"独立层 → 并入"玉衡"作为校准的因果链诊断子能力
- 玉衡从原"情景层/What-if"重定义为**反向校准通道**（天玑 → 天枢/天璇 权重写回）
- 摇光从"进化层"降级为**横切 SRE 层**（监控/告警/rollback），不进数据流
- 物理上只保留 **4 个容器**：macro-scan / macro-sim / crucix / rsshub；天玑/玉衡/开阳作为 macro-scan 热挂载区的逻辑模块（共享容器）

## 1. 缘起 — 为什么要重审

**触发事实**（`01_事实地基.md` 已代码级核实）：

1. **数据源扩张失控**：16 类 → 22 类，但其中 **9 个孤儿源**（BDI/FAO/航班/商品/加密冗余/EIA/中观/新闻/HDX）落盘无人用。22 源中实际喂 GRV 的不到 13 维，剩余只是"采集为了采集"。
2. **GRV 维度膨胀但部署漂移**：源码写了 11 维（含 seismic_risk/energy_grid_risk），但实测 `grv_latest.json` 仅 8 维，climate_risk=0.0——**容器跑的可能不是最新代码**，是部署漂移而非设计缺陷。
3. **校验回路完全开环**：预测→Brier 评分存在，但结果只 print/人工看，不反哺任何权重或阈值——99% 的可能 22 源里有预测力的源被埋在噪声里、无预测力的源却享受高权重。
4. **Crucix 职责模糊**：独立容器 :3117 在天枢的 8s timeout 实时调用，**与天枢的 fetcher 在 EIA 上重复采集**；ACLED 放弃的事天枢不知道。两个系统的能力矩阵从未同步。
5. **原 7 层与现实严重脱节**：实际运行的只有天枢 + 天璇；天玑只有 DRAFT v0.1；天权/玉衡/开阳/摇光 4 层**无任何代码、无 PRD、无时间线**。"北斗七星"成了愿景画饼。

**结论**：再画一层比解决一层难。先回答"现有 2 层 + 1 草稿要不要扩到 N 层、N 是几、每层干什么"。

## 2. 设计方法 — 一次一个维度（Q1→Q15 压缩）

下面把提示词的 15 个问题按推理脉络压缩为 5 个真正的判断点，避免逐题回答（用户期望立即交付最终方案，不是分轮确认）。

### 2.1 第一判断：现有问题到底在第几层

**校验开环（prediction → Brier → print）**——这个最痛的痛点，不是天枢的问题，也不是天璇的问题，而是**缺一层"天玑"**做事后验证。这是为什么天玑 DRAFT v0.1 早就该启动——但没人推，因为都在画"完美 7 星"。

**Crucix 与天枢职责重叠（EIA 重复采集）**——这是**横向切分**问题，不是层数问题。解法不是砍层也不是加层，是划清"什么归谁"。

**9 个孤儿源无消费**——这是**接线**问题，不是层数问题。解法是天枢内部补接线（已在 `00_终裁_架构演进优先级.md` Tier 1 列入 T1-1）。

**部署漂移**——这是**运维**问题，跟层数无关。

→ **唯一必须补的"层"：天玑（验证层）**。其他问题都不靠加层解决。

### 2.2 第二判断：北斗命名的契合度

依 `北斗七星架构_深度评估_20260729.md` 已做过的命名学分析：

| 星 | 候选职责 | 古义契合度 | 决策 |
|---|---|---|---|
| **天枢** | 观测 | 极好（斗勺之首，定方向） | ✅ 保留 |
| **天璇** | 仿真 | 好（辨距） | ✅ 保留 |
| **天玑** | 验证 | 极好（玑衡之机，精密校准） | ✅ 保留（DRAFT v0.1 已就位）|
| **天权** | 知识层/决策 | 🟡 名字偏"平衡权重"，与"决策/知识"略偏 | ⚠️ 砍独立层，并入玉衡 |
| **玉衡** | 情景/What-if | 🟡 与天玑职能重叠（古义是"衡定标准"=校准）| ⚠️ 重定义为"反向校准通道" |
| **开阳** | 交互/发布 | 🔴 武曲星 ≠ 交互 | ✅ 用，但承认命名凑合 |
| **摇光** | 自主进化 | 🟡 偏"破旧立新"，更像 SRE | ⚠️ 降级为横切 SRE 层 |

→ **结论：天枢/天璇/天玑 命名契合不动，天权并入玉衡，玉衡重定义，摇光降级。开阳保留但承认命名不完美。**

### 2.3 第三判断：每层职责"非他莫属"

按"非他莫属"原则检验：

- **天枢**：管 22 类数据源的采集/落盘/时序积累/GRV 合成 → **非他莫属**（没有其他层能做采集）
- **天璇**：管 12-Agent 蒙特卡洛/概率路径树 → **非他莫属**（天枢做不了仿真）
- **天玑**：管预测存档/到期自动评分/准确率面板/校准建议 → **非他莫属**（天璇做完不知道对不对，天枢不知道预测存在）
- **玉衡**：管把天玑的校准建议**写回**天枢 GRV 权重 / 天璇 agents.yaml → **非他莫属**（必须独立成环节，否则验证结果永远 print 不闭环）
- **开阳**：管 ntfy 推送/WebUI/准确率面板的统一呈现 → **非他莫属**（当前零散的多入口需要聚合）
- **Crucix（横切）**：管非结构化实时信号采集 + LLM prompt 注入 → **非他莫属**（天枢的批量调度 06:00 模式做不到 8s timeout 实时）
- **摇光（横切）**：管全层健康监控/告警/rollback → **非他莫属**（必须横切而非末端后处理，否则每层各写各的监控，3 个月后会漂移）

→ 7 个逻辑层都通过"非他莫属"测试。**问题不是要不要 7 层，而是其中 4 层物理上是否可以共用容器。**

### 2.4 第四判断：物理层 vs 逻辑层

**个人 NAS + Docker + 单一开发者**——每多一个容器 = 多一份 Dockerfile、多一份 deploy.sh 分支、多一份日志路径、多一份 restart 流程。**复杂度是债务**。

但 7 个逻辑层若强行塞进 1 个容器，会变成 monolith，反而更糟（重启粒度变粗、隔离失败）。

**物理折中（4 容器）**：

| 容器 | 包含逻辑层 | 理由 |
|---|---|---|
| **macro-scan**（天枢） | 天枢 + 天玑 + 玉衡 + 开阳（部分） | 这 4 个都基于"日级调度 + 数据落盘"，时间尺度匹配，**热挂载区天然共享代码空间** |
| **macro-sim**（天璇） | 天璇 | 仿真 CPU 重、COPY 模式重建成本可控，独立合理 |
| **crucix** | Crucix（实时信号总线） | 实时调用模式（8s timeout）vs 批量调度（06:00）本质不同，独立 |
| **rsshub** | RSS 代理 | 中文新闻代理，纯转发，独立 |

**逻辑层 = 7、物理容器 = 4。** 命名仍叫"7 层框架"，但用户感受到的运维负担是 4 个 docker container。

### 2.5 第五判断：合并与砍层的最终边界

**砍掉的层：**
- ❌ **天权独立层**（知识层/决策）—— 拆解为：(a) ChromaDB 维护保留在天枢现有能力内（无需独立层）；(b) 因果链建模并入"玉衡"作为校准诊断的子能力（校准需要因果链解释"为何这维失准"，独立成层会跟玉衡职能重叠 80%）。

**合并/重定义的层：**
- 🔁 **玉衡**——从原"情景层/What-if 离线推演"重定义为"反向校准通道"。理由：(a) What-if 已是天璇 `run_macro_analysis --event` 的现有能力，不需独立层；(b) 校验开环是真痛点，独立叫"玉衡"反而凸显；(c) 命名学上"玉衡管"=衡定标准=校准，契合度更高。

**降级为横切的层：**
- ⬇️ **摇光**——从原"进化层"降级为"横切 SRE"。理由：(a) "自主进化"听上去美但当前无 ground truth 无从进化；(b) 监控/告警/rollback 是横切关切，任何一层都该被监控，不是流水线末端后处理；(c) 物理上可作为 macro-scan 热挂载区的一个模块（`ops/sre.py`），不增加容器。

**升格为正式层的组件：**
- ⬆️ **Crucix**——从"无名的外部依赖"升格为"实时信号总线"。理由：见 §4。

### 3.2 每层详解

#### ▎天枢 Dubhe（观测层）— macro-scan v3.6.5
- **职责**：
  - 22 类数据源采集、清洗、时序积累
  - GRV 11 维合成（含归一化、加权、告警阈值判断）
  - LLM 日报生成（run_macro_analysis.py，注入 Crucix 实时信号）
  - 历史积累（grv_history.jsonl + 各 fetcher `_history.jsonl`）
- **包含现有模块**：`核心代码/*.py`、`scheduler.py`、`run_macro_analysis.py`
- **接口 / 契约**：
  - **输出**：`data/grv_latest.json`（v1.0 schema）、`data/sim_trigger.json`、`data/news_export.json`、`data/predictions_log.json`
  - **被调用**：Crucix `/api/data` 8s timeout；天璇 daemon 监听 `sim_trigger.json`
- **不做什么**：
  - 不做预测准确率评分（归天玑）
  - 不做 What-if 推演（归天璇 `run_macro_analysis --event`）
  - 不做因果链建模（并入玉衡子能力）
  - 不做系统自监控（归摇光）
- **复杂度代价**：1 个容器（既有），代码量约 6000+ 行（macro-scan 全部核心代码）。

#### ▎天璇 Merak（仿真层）— macro-sim v2.0.13
- **职责**：
  - 12-Agent Monte Carlo × 100，概率路径树聚类（≥5% 概率）
  - 校准循环（calibrator.py，前 50 步对历史）
  - LLM 叙事生成（bifurcation._generate_narrative，GLM-Z1-9B）
  - WebUI 渲染（reports/*.md + ECharts）
- **包含现有模块**：`core/*.py`、`agents/{financial,geopolitical,social}.py`、`run.py`
- **接口 / 契约**：
  - **输入**：读 `data/grv_latest.json`、`data/fred_history/*.csv`、`data/news_export.json`、`data/sim_trigger.json`
  - **输出**：`reports/{日期}_{时}_演化_L{level}_校准{score}.md`、`sim_log.db`
- **不做什么**：
  - 不做观测（归天枢）
  - 不做事后验证（归天玑）
  - 不做参数自动校准写回（归玉衡）
- **复杂度代价**：1 个容器（既有），COPY 模式重建约 2-3 分钟。

#### ▎天玑 Phecda（验证层）— NEW（基于 DRAFT v0.1 升级到 V1）
- **职责**：
  - 预测存档（prediction_ledger.db，从 macro-sim 报告提取可验证主张）
  - 自动评分（verify_predictions.py + forecast_tracker.py 整合为单一 worker）
  - 准确率面板（accuracy_dashboard.html，扩展 :8899 新路由 `/accuracy`）
  - 校准建议生成（写 verify_result.json，触发玉衡写回）
- **包含现有模块**：`核心代码/verification.py`（新建）、`forecast_tracker.py`（接管）、`verify_predictions.py`（接管）
- **接口 / 契约**：
  - **输入**：`reports/*.md`、`data/grv_history.jsonl`、`data/fred_history/*.csv`、`data/predictions_log.json`
  - **输出**：`data/verify_result.json`、`verification/prediction_ledger.db`、`verification/accuracy_dashboard.html`
- **不做什么**：
  - 不写回任何 GRV 权重（归玉衡）
  - 不做任何实时告警（仅月度 cron + 手动查看）
  - 不预测未来（归天璇）
- **复杂度代价**：**新增模块**，不新增容器——作为 macro-scan 热挂载区的 `verification/` 子目录。代码量预计 800-1200 行（含 SQLite schema + LLM 提取 + Brier 评分）。

#### ▎玉衡 Alioth（反向校准通道）— NEW（重定义自原"情景层"）
- **职责**：
  - 读 `verify_result.json`（天玑产出）
  - 生成 GRV 维度权重调整建议（`suggested_weight_adjustments`）

  - **因果链诊断**（天权并入能力）：当某维 GRV 失准时，检索 ChromaDB + 历史危机库，解释"为何失准"
- **包含现有模块**：新建 `核心代码/calibrator_writer.py`、新增 `agents.yaml_writer.py`（macros-sim 端 COPY 模式需 rebuild）
- **接口 / 契约**：
  - **输入**：`data/verify_result.json`、ChromaDB 向量库、`core/world_state.py` 内生变量
  - **输出**：`config/grv_weights.yaml`（天枢读取）、`agents.yaml`（天璇读取）
- **不做什么**：
  - 不做正向推理/推演（归天璇）
  - 不做事后验证（归天玑）
  - 不做实时决策建议（用户自己判断）
- **复杂度代价**：**新增模块**，不新增容器。代码量预计 400-600 行（读 JSON + 写 YAML + 因果链诊断 RAG 查询）。

#### ▎开阳 Mizar（呈现/发布层）— 升级（扩展既有 WebUI + 新准确率面板）
- **职责**：
  - ntfy 推送（`macro-tsx-9005`，既有）
  - WebUI :8899（既有）+ `/accuracy` 新路由（天玑产出）
  - 统一仪表板（dashboard.py，工作日 20:30）

- **包含现有模块**：`webui/index.html`、`webui/app.js`、`dashboard.py`
- **接口 / 契约**：
  - **输入**：所有层契约文件 + `verification/accuracy_dashboard.html`
  - **输出**：HTTP 响应（WebUI）+ ntfy push 消息
- **不做什么**：
  - 不做业务逻辑（任何计算都归上层）
  - 不做数据持久化（只读）
- **复杂度代价**：纯前端扩展，无新容器。代码量新增约 200-400 行（准确率面板路由 + 仪表板聚合视图）。

#### ▎Crucix（实时信号总线）— 横切层，重新定义
- **职责**：
  - 实时多源情报采集（gscpi/nuke/sdr/air + 内部 EIA/FIRMS）
  - LLM prompt 格式化注入（`/api/data` 8s timeout）
  - 与天枢的边界：**管"非结构化实时信号"，不管"结构化时序"**
- **物理**：独立容器 :3117（**不动**）
- **接口**：单一标准 API `/api/data?type=<signal_type>`
- **与天枢的分工决策规则**：
  - 能落盘成时序（CSV/JSON）且日级可消费的 → **归天枢**（FRED/GPR/GDELT/地震/航班/CoinGecko等）
  - 一次性情报或需 LLM 即时解析的实时信号 → **归 Crucix**（gscpi/nuke/sdr/air、前瞻性情报）
- **不做什么**：
  - 不做日级批量调度（天枢的事）
  - 不做结构化时序存储（天枢的 JSONL）
  - 不做仿真（天璇的事）

#### ▎摇光 Alkaid（自主运维/SRE）— 横切层，降级自原"进化层"

## 4. Crucix 最终定位 — 选择 D

### 4.1 为何不是 A/B/C

| 方案 | 否决理由 |
|---|---|
| **A 维持现状** | 两个系统各自膨胀、EIA 重复采集、ACLED 放弃的事天枢不知道——维持即放任职责重叠加重 |
| **B 吸收进数据层** | 天枢 fetcher 已 22 个，再加 4 个会膨胀到 26；且 Crucix 的 8s 实时调用模式 vs 天枢 06:00 批量调度模式本质不兼容，强行并入会让天枢 scheduler 复杂度爆炸 |
| **C 扩展为对外门户** | 当前 Crucix 只被天枢调用，没有"对外"使用场景；做门户等于造一个永远空着的 WebUI |
| **D 重定义为实时信号总线** | ✅ 最契合实际：Crucix 本质就是"实时信号→LLM prompt 注入"的标准化通道，把它明确划为横切层，**划清"结构化时序归天枢、非结构化实时信号归 Crucix"的边界**，两个系统的职责重叠问题自动消失 |

### 4.2 Crucix 在新框架中的位置

```
[外部实时信号源]                [天枢 LLM 链路]
gscpi / nuke         ┌─────────┐    ┌──────────────┐
sdr / air            │ Crucix  │    │ run_macro_   │
+ 内部 EIA/FIRMS ───▶│ :3117   │───▶│ analysis.py  │
                     │ 8s      │8s  │ (注入 prompt)│
                     └─────────┘    └──────────────┘
                          ↑
                          │ 横切调用
                     （不是天枢的子模块，也不是独立的一层）
```

### 4.3 与天枢的分工决策规则

**凡满足以下任一条件的源 → 归 Crucix：**
1. 单次查询，无历史积累需求（gscpi 的瞬时供应链压力分数）
2. 需要 LLM 即时解析的非结构化文本（nuke 信号的事件描述）
3. 调用模式是"事件触发 + 8s 内必须返回"而非"定时拉取 + 落盘"

**凡满足以下任一条件的源 → 归天枢：**
1. 可落盘成 CSV/JSON 时序
2. 日级或更低频更新
3. 需被 GRV 合成、归一化、加权

**当前清单执行结果：**
- 天枢已有 22 源全部符合"天枢归"标准，**不动**
- Crucix 内部 EIA/FIRMS：**待审计**——EIA 是周~月频可落盘（符合天枢归），但 Crucix 用 8s 实时调用做 LLM 注入。要么 EIA 完全归天枢（fetch_energy_eia.py 已存在），Crucix 删 EIA 模块；要么 EIA 留在 Crucix 但仅做"前瞻性 EIA 解读"，不做结构化时序。**此决策建议 Phase 1 完成审计后再定（见 08 路线图 T1-3）。**

## 6. 边界与不做的事

**明确划出去不做的事**（避免范围蔓延）：

- ❌ **不做分布式**——单 NAS 单机部署，不引入 Kubernetes、不分片数据库。LLM 配额是 quota 不是 scale 问题。
- ❌ **不做用户系统**——个人内部研究系统，无登录、无权限、无多租户。WebUI 假设为局域网内可信访问。
- ❌ **不做移动 App**——ntfy 已覆盖手机推送场景，再做 App 是过度工程。
- ❌ **不做实时低延迟告警**——所有层都是日级或月度调度，不做秒级事件流。Crucix 的 8s timeout 是 LLM 调用限制，不是"实时"承诺。
- ❌ **不做通用知识图谱**——天权的因果链作为玉衡子能力存在，**不**独立成图数据库、不做本体建模、不做 NER/RE 抽取。ChromaDB 现有 RAG 足够。
- ❌ **不做 GRV 全自动自校准**——玉衡的校准建议**只生成**给用户看，**不自动写回**任何常量。第一年人工 review，第二年再考虑自动化。
- ❌ **不做 7 层物理容器化**——4 容器是上限。任何新模块若要求独立容器，必须先证明不能合并到 macro-scan 热挂载区。
