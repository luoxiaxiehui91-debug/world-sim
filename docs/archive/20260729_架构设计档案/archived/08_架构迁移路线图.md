# 08 架构迁移路线图

> 日期：2026-07-29  
> 配套：`07_北斗七星架构设计.md`（最终方案）  
> 方法：Tier 0-3 优先级排序（继承 `00_终裁_架构演进优先级.md`）+ 5 主层 + 2 横切的实施分解  
> 原则：复杂度是债务；任何新增模块先看是否能合并到 macro-scan 热挂载区

## 总览：四阶段 + 一交付

```
Phase 0 (立即, 本周)      Phase 1 (本周内)        Phase 2 (本季度)         Phase 3 (下一阶段)
━━━━━━━━━━━━━━━━━━━    ━━━━━━━━━━━━━━━━━━    ━━━━━━━━━━━━━━━━━━━    ━━━━━━━━━━━━━━━━━━━
🟥 阻塞性纯调查          🟨 天玑 V1 + 玉衡骨架    🟩 天玑 V2/V3 自动化     🟦 摇光 SRE 层
```

## Phase 0：阻塞性纯调查（24-72 小时内，必做）

> 阻断所有下游：**不查清事实，所有接线/解冻/告警都是在事实真空里搭楼**（`00_终裁_架构演进优先级.md` 原话）

### T0-1 部署漂移根因定位
- **动什么**：在容器内实跑 `docker exec macro-scan-macro-scan-1 python3 /app/geo_risk_vector.py`，核对产出的 `grv_latest.json` 字段
- **影响范围**：仅 `geo_risk_vector.py` 单文件，影响天枢对外契约
- **风险**：🟢 低（纯只读核查，不改任何代码）
- **回滚**：无（纯调查）
- **验收**：`grv_latest.json` 字段数 = 源码定义字段数；如不一致，需定位是 deploy.sh 没同步、还是 bind-mount 没生效、还是 fetcher_base.py 不同步
- **Owner**：天枢维护者（单一开发者）

### T0-2 R08 资产相关性突变输入源审计
- **动什么**：读 `signal_synthesizer.py` `_check_asset_correlation_shift`（约 L302-394），确认 4 个资产对（VIX/DGS10、WTI/VIX、BAA10Y/T10Y2Y、DTWEXBGS/BAA10Y）数据来自哪个 fetcher
- **影响范围**：仅 R08 规则，影响合成信号质量
- **风险**：🟡 中（如果 R08 当前在无时序源上跑，可能正在生产假信号，是潜在的**在线 bug**）
- **回滚**：将 R08 加 feature flag 临时禁用
- **验收**：白纸黑字确认输入源；若为无时序源（crypto/fx/world 等 latest 快照）→ 标记为已知失效 + 在 `_check_asset_correlation_shift` 入口加时序长度校验
- **Owner**：天枢维护者

### Phase 0 风险与回滚
- **风险**：低，纯调查无写入
- **回滚**：无
- **阻断**：T0-1/T0-2 任一未完成，禁止进入 Phase 1 的孤儿源接线

## Phase 1：本周内可动（7 天内）

> **目标**：天玑 V1 骨架立起来、孤儿源历史抢救、Crucix 边界明确  
> **物理变更**：仅在 macro-scan 热挂载区新增 `verification/` 子目录 + 修改 Crucix 容器内 EIA 配置；不新增容器

### T1-1 孤儿源 `_history.jsonl` 追加器
- **动什么**：为 energy_eia / bdi / fao_food_price / fx_latest 加历史追加器（接在各源落盘**之后**）；强隔离（每源独立 try/except）、heartbeat（日采末尾打"处理N源/写M行/跳K"）、滚动清理（行数上限或按月归档）
- **影响范围**：仅 macro-scan 容器内 4 个 fetcher 文件，无对外契约变更
- **风险**：🟢 低（纯 additive，出错只脏一个隔离 log）
- **回滚**：删追加器即回滚，主管道零残留
- **验收**：每源独立 try/except 生效（故意让 EIA 失败不影响 BDI）；heartbeat 输出可见；行数上限生效
- **Owner**：天枢维护者
- **依赖**：无（与 T0-1/T0-2 并行）

### T1-2 可观测性计数器
- **动什么**：synthesizer 触发计数、LLM 配额消耗、ntfy 发送量、Live/shadow 分流标记，写固定 log `data/observability_YYYY-MM-DD.json`
- **影响范围**：scheduler.py + signal_synthesizer.py，仅追加 log 写入
- **风险**：🟢 低（不改任何决策数据）
- **回滚**：删日志钩子
- **验收**：计数器写固定 log；Live/shadow 分流标记可读
- **Owner**：天枢维护者
- **依赖**：无

### T1-3 Crucix 边界审计（解决 EIA 重复采集）
- **动什么**：审计 Crucix 内部 EIA/FIRMS 模块的去留
  - 选项 A：完全归天枢（fetch_energy_eia.py 已存在），Crucix 删 EIA 模块
  - 选项 B：Crucix 保留 EIA 但仅做"前瞻性 EIA 解读"（LLM 即时分析），不做结构化时序
  - 决策依据：审计 EIA 调用模式（是 8s 实时还是批量）；若 Crucix 的 EIA 调用频率 ≤ 日 1 次 → 完全归天枢
- **影响范围**：Crucix 容器 + macro-scan 的 `fetch_energy_eia.py`
- **风险**：🟡 中（可能影响 run_macro_analysis.py 的 Crucix prompt 注入质量）
- **回滚**：回 git 即可
- **验收**：EIA 在两边的职责明确分离，无重复采集
- **Owner**：天枢维护者 + Crucix 维护者（实际是同一人）
- **依赖**：无

### T1-4 天玑 V1 启动（手动存档 + GRV 方向性自动评分）
- **动什么**：基于 `tianji-design.md` V1 计划，新建 `核心代码/verification.py`，包含 SQLite 建表 + 人工录入 + GRV 方向性自动评分。从现有 `docs/仿真报告/*.md` 人工识别已到期预测，手动录入
- **影响范围**：macro-scan 容器内新增 1 个模块；不新增容器
- **风险**：🟡 中（V1 是骨架，立 schema 后难改）
- **回滚**：删 `核心代码/verification.py` + `verification/` 目录
- **验收**：(1) prediction_ledger.db 建表成功；(2) 录入 ≥ 10 条历史预测；(3) GRV 方向性预测用 `grv_history.jsonl` 自动评分能产出第一份准确率报告
- **Owner**：天玑建设者（建议为天枢维护者，因共享容器）
- **依赖**：T0-1（须知道回放的是哪份 GRV 逻辑）

### Phase 1 风险与回滚
- **总风险**：🟡 低-中（纯 additive 为主）
- **回滚**：每项独立可回滚，互不影响
- **关键检查点**：Phase 1 末必须看到天玑第一份准确率报告，否则 V2/V3 缓做

## Phase 2：本季度内（30 天内）

> **目标**：闭环验证（天玑 V2/V3 自动化）+ 玉衡 V1 校准写回 + 开阳 V1 准确率面板  
> **物理变更**：天璇 COPY 模式 rebuild 一次（agents.yaml 写入器）

### T2-1 离线回测闸门（解冻 STAGING_MODE 的 go/no-go）
- **动什么**：用**既有**的 news.db / gdelt_history 回放过去 30-90 天；产出"若 Live 会触发几次告警、吃几次 LLM 配额"报告
- **影响范围**：仅离线分析，无 Live 影响
- **风险**：🟢 低（纯离线分析）
- **回滚**：无
- **验收**：报告须标注"旧数据 + 新逻辑"的一致性风险；给出 go/no-go 建议
- **Owner**：天枢维护者
- **依赖**：T0-1（须知道回放的是哪份逻辑）

### T2-2 玉衡 V1 校准写回（人工审批模式）
- **动什么**：新建 `核心代码/calibrator_writer.py`，读 `verify_result.json` 生成 `suggested_weight_adjustments`，**写到一个待审批文件** `data/pending_weight_adjustments.yaml`，**不自动写回**任何常量。新建 `core/agents/agents.yaml_writer.py`（macros-sim 端），同样只写待审批文件 `agents_pending.yaml`
- **影响范围**：macro-scan + macro-sim 两个容器；COPY 模式重建一次
- **风险**：🟠 中（写回参数错误会导致天枢/天璇双双走偏）
- **回滚**：回 git + 删 pending 文件
- **验收**：玉衡能从天玑产出 → 生成建议 → 写待审批文件；用户人工 review 后手动 cp 到 `geo_risk_vector.py` 常量（GRV 维度权重）或 `agents.yaml`（天璇）
- **Owner**：天玑建设者 + 天璇维护者（共享维护者）
- **依赖**：T1-4（天玑 V1 跑起来）

### T2-3 天玑 V2 自动提取（LLM 解析 macro-sim 报告）
- **动什么**：扩展 `verification.py`，从 macro-sim 报告自动提取可验证主张，写入 ledger
- **影响范围**：仅 macro-scan 容器
- **风险**：🟡 中（LLM 提取可能不准确，需人工 spot-check）
- **回滚**：删 V2 提取逻辑，保留 V1 手动录入路径
- **验收**：从 5 份历史报告自动提取，提取结果人工 spot-check ≥ 80% 准确
- **Owner**：天玑建设者
- **依赖**：T1-4

### T2-4 天玑 V3 自动验证（月度 cron）
- **动什么**：新增月度 cron job，对到期预测自动评分，生成准确率面板
- **影响范围**：scheduler.py 新增 1 个 cron
- **风险**：🟢 低（纯只读评分）
- **回滚**：注释 cron
- **验收**：每月 1 日 cron 触发；评分结果写 `accuracy_summary` 表
- **Owner**：天玑建设者
- **依赖**：T2-3

### T2-5 开阳 V1 准确率面板
- **动什么**：在 macro-scan WebUI :8899 新增 `/accuracy` 路由，读天玑 `prediction_ledger.db` 渲染准确率表
- **影响范围**：仅前端
- **风险**：🟢 低
- **回滚**：删路由
- **验收**：浏览器访问 `:8899/accuracy` 看到准确率表（总数/正确/准确率/M3 解锁进度）
- **Owner**：开阳建设者
- **依赖**：T1-4 + T2-4

### T2-6 玉衡 V2 因果链诊断（天权并入能力首次落地）
- **动什么**：在 `calibrator_writer.py` 中，当某维 GRV 持续失准时，检索 ChromaDB + 历史危机库，生成自然语言诊断"为何失准"
- **影响范围**：仅 macro-scan 容器
- **风险**：🟡 中（LLM 诊断可能不可靠）
- **回滚**：删 V2 诊断逻辑，保留 V1 数值调整建议
- **验收**：选 1 个历史失准维度（如 sanctions_risk），因果链诊断能引用 ≥ 3 条历史案例
- **Owner**：玉衡建设者
- **依赖**：T2-2

### Phase 2 风险与回滚
- **总风险**：🟡-🟠 中（首次涉及写回、LLM 解析、跨容器协同）
- **回滚**：每项独立可回滚；Phase 2 任意失败不阻塞 Phase 3 计划（按反馈调整）
- **关键检查点**：Phase 2 末必须看到玉衡人工审批的第一次权重调整落地

## Phase 3：下一阶段（看 Phase 1/2 反馈再定，60-90 天后启动）

> **目标**：把横切层补齐（SRE/自主运维）  
> **原则**：Phase 1/2 反馈决定是否启动；不可提前承诺

### T3-1 摇光 SRE 层 V1（健康监控 + 自动 rollback）
- **动什么**：扩展 macro-scan 现有 `observability.py`，新增 (a) macro-sim 容器健康检查（每 10 min）；(b) LLM 配额/Crucix 健康/孤儿源连续 3 天未更新检测；(c) 自动 rollback（检测到 GRV 字段数与源码定义不一致时自动 git pull 稳定版）
- **影响范围**：macro-scan 容器
- **风险**：🟡 中（自动 rollback 误触发可能丢数据）
- **回滚**：feature flag 关闭自动 rollback
- **验收**：3 种异常场景（容器挂/LLM 超限/字段漂移）能被摇光检测并触发 ntfy 告警
- **Owner**：摇光建设者
- **依赖**：Phase 1 T1-2 可观测性计数器（已就位）

### T3-2 摇光 SRE 层 V2（异常检测 + STAGING 解冻闸门）
- **动什么**：基于 T2-1 离线回测报告，若 go → 解冻 STAGING_MODE（按 `00_终裁_架构演进优先级.md` Tier 3 T3-2 流程）；扩展摇光监控信号共振规则的触发频率
- **影响范围**：signal_synthesizer.py + scheduler.py
- **风险**：🟠 中-高（解冻后误触发可能吃光 LLM 配额）
- **回滚**：feature flag 重新冻结
- **验收**：解冻后 7 天内 LLM 配额消耗 ≤ 0.5 次/日（远低于 daily_llm_limit=2）
- **Owner**：摇光建设者
- **依赖**：T2-1 + Phase 1 跑满 30 天

### T3-3 天权因果图谱（按需启动）
- **触发条件**：仅当 T2-6 因果链诊断发现"纯文本 + ChromaDB 检索"不够用（如需要查询"X 事件后历史上哪些维度同时受影响"）
- **动什么**：评估是否引入轻量图结构（networkx + JSON 持久化，**不引入 neo4j**）
- **影响范围**：玉衡子模块
- **风险**：🟡 中
- **回滚**：删图结构模块
- **验收**：能在 ≤ 1s 内回答"X 事件后历史上 Y 维度同时受影响的次数"
- **Owner**：天权建设者（按需）
- **依赖**：T2-6 + 用户明确需求

### Phase 3 风险与回滚
- **总风险**：🟡-🟠 中（涉及自动 rollback、解冻、按需模块）
- **回滚**：每项独立可回滚；Phase 3 任一任务失败不阻塞 Phase 4（暂未规划）
- **关键检查点**：Phase 3 末应有 ≥ 3 类异常被摇光自动监控；STAGING 解冻后 30 天 LLM 配额消耗稳定
