## 0. 为什么需要这份文档

07 文档对 Crucix 的定性是**"实时信号总线"（横切层）**——只关注了它的数据采集/LLM 注入能力。但经过 GitHub 调研（`github.com/calesthio/Crucix`），发现 Crucix 实质上是：

> **27 个 OSINT 源的 Jarvis 风格 HUD 仪表板**，带 3D WebGL 地球、9 种标记类型、区域筛选、实时市场数据、风险仪表盘、SSE 自刷新——**且已有 LLM 对话交互能力**（/brief、/sweep、Telegram/Discord Bot）。

这意味着 Crucix **同时具备**数据采集和可视化两层能力。07 文档的方案只用了它的采集侧，**可视化侧被完全浪费了**。

本文档回答：开阳层是应该从 Crucix Web UI 扩展，还是从天枢 :8899 扩展。

---

## 1. 对比：两个 UI 基座

| 维度 | 天枢 WebUI (:8899) | Crucix Web UI (:3117) |
|------|---------------------|------------------------|
| 技术栈 | Python + ECharts | Node.js + Globe.gl (WebGL) + SSE |
| 可视化能力 | 三面板：GRV 表 + 日报 + 数据源状态 | 3D 地球 + 9 标记类型 + 3D 飞行走廊弧线 + 区域筛选 |
| 实时性 | 页面需手动刷新 | SSE 自刷新（15 分钟 sweep） |
| 交互能力 | 只读查看 | LLM 对话（/brief /sweep）+ Telegram/Discord Bot |
| 数据来源 | 天枢内部数据 | 独立 27 源（含自定义信号 gscpi/nuke/sdr/air） |
| 扩展性 | 新增面板需改 HTML/JS | 模块化（dashboard/apis/lib），易加新数据源 |
| 当前角色 | 天枢运维查看面板 | 自主情报终端 |
| LLM 集成 | 无（在天枢后端） | 有（多 provider 支持） |

**结论：Crucix 的 Web UI 在可视化、实时性、交互能力三个维度上都显著优于天枢 :8899。**

## 2. 开阳层的两种实施方案

### 方案 A：天枢 :8899 扩展（07 文档方案）

```
开阳 = :8899（现有）+ /accuracy 新路由 + :8900 新面板
```

**流程**：天枢 WebUI 扩展 → 读天玑 prediction_ledger.db → 渲染准确率面板

**优点**：
- 代码全在 macro-scan 容器内，零跨容器依赖
- 开发路径最短（改既有 HTML/JS）
- 与 07 文档路线图完全对齐

**缺点**：
- 可视化能力贫瘠（ECharts 能做图表但做不了 3D 地球 / 地图热力）
- 每次加新面板需要从头写 UI，无模块化基础
- :8899 仅为天枢服务，永远达不到"统一仪表板"的目标
- **Crucix 已有的优秀 UI 完全浪费**

### 方案 B：Crucix :3117 扩展（本文档推荐）

```
开阳 = Crucix Web UI（基座）+ 天枢/天璇/天玑 数据源注入
```

**流程**：Crucix 本身就是一个模块化仪表板，新增数据源接入即可：
1. 天枢 GRV 时序 → 新增 "GRV Trends" 面板（可落成折线图/热力图）
2. 天枢日报摘要 → 注入 Crucix OSINT 信息流（同级展示）
3. 天璇仿真路径树 → 新增 "Simulation Paths" 面板（概率树可视化）
4. 天玑准确率面板 → 新增 "Verification" 面板（Brier 趋势 + 校准建议）

**优点**：
- **直接复用 Crucix 的 3D 地球 + 实时刷新 + LLM 对话**，开阳层从"从零开发"变成"加面板"
- 用户已经习惯 Crucix 的 UI 交互模式，学习成本为零
- 模块化架构天然支持"统一仪表板"——不同数据源只是不同面板
- 天枢/天璇/天玑的数据和 Crucix 自有数据在同一界面并排展示，真正实现"跨域关联"
- LLM 对话能力可以直接查询天枢/天璇/天玑的数据（/brief 今天 GRV？/sweep 推演路径？）

**缺点**：
- Crucix 是 Node.js/Express，天枢是 Python，跨语言调用需要接口适配
- 需要在 Crucix 代码中新增几个 API 适配器 / 数据面板组件
- 天璇 macro-sim 的数据接口需要额外暴露（当前无 HTTP API，只有文件契约）
- 技术债：Crucix 由外部开源社区维护，版本升级可能与自定义面板冲突
- 当前部署在独立容器，数据面板需要能跨容器读取天枢的 JSON 文件（需要 volume 挂载或 HTTP API）

## 3. 推荐方案：B-混合（分阶段）

考虑到 07 文档的路线图已经有明确的时间线，直接推翻重来不现实。推荐**分阶段融合**：

### Phase 1（不变，按 07 路线图）

开阳层先按 07 方案走——在天枢 :8899 新增 `/accuracy` 路由。这一阶段的目标是**天玑跑通，拿到第一份准确率报告**，不涉及 UI 框架切换。

### Phase 2（调整）

在 T2-5 准确率面板的基础上，**开始向 Crucix 注入数据**：

| 步骤 | 内容 | 优先级 |
|------|------|--------|
| P2a | 在 Crucix 中新增 "GRV Trends" 面板，读 `data/grv_latest.json` | 高 |
| P2b | 在 Crucix 中新增 "Daily Report" 面板，读天枢日报摘要 | 高 |
| P2c | 在 Crucix 中新增 "Simulation" 面板，读天璇报告文件 | 中 |
| P2d | 在 Crucix 中新增 "Verification" 面板，读天玑 prediction_ledger.db | 中 |
| P2e | 评估 :8899 是否可以退役（所有面板都迁移到 Crucix 后） | 低 |

### Phase 3（远期）

如果 P2a-P2d 全部完成且用户满意：
- :8899 降级为纯管理面板（调度状态、日志查看）
- Crucix :3117 成为"世界推演系统统一仪表板"
- 开阳层正式从"天枢子模块"演变为"Crucix 扩展"

如果 P2 推进中发现 Crucix 代码改造难度过大：
- 退回方案 A，继续在 :8899 上迭代
- Crucix 保持独立情报终端定位，不与天枢/天璇/天玑融合

## 4. 对 07 架构文档的修正建议

07 文档的架构本身（5 主层 + 2 横切）**不需要改**，但以下 3 处需要补充：

### 4.1 开阳层的物理容器

07 §2.4 表格：

> | macro-scan（天枢） | 天枢 + 天玑 + 玉衡 + 开阳（部分） |

应改为：

> | macro-scan（天枢） | 天枢 + 天玑 + 玉衡 |
> | crucix | Crucix（实时信号总线） + 开阳（统一仪表板基座） |

开阳的"呈现"能力**物理上合署到 Crucix 容器**，而不是 macro-scan。理由：(1) Crucix 已有成熟的 Web UI + SSE 实时刷新架构；(2) 天枢 :8899 是简单的 ECharts 页面，不具备作为统一仪表板的扩展基础。

### 4.2 开阳层的职责描述

07 §3.2 开阳段应补充：

> **基座选择**：Phase 1 沿用 :8899（快速验证），Phase 2 起逐步迁移到 Crucix Web UI。最终状态：Crucix :3117 作为统一仪表板，:8899 保留为运维管理面板。

### 4.3 信息深度对照表补充

07 §3.3 表格中应新增一行：

> | Layer 10 统一呈现（新增） | Crucix Web UI + 天枢/天璇/天玑面板接入 | 开阳（合署到 Crucix 容器） | ⚠️ Phase 2 启动 |

## 7. 总结

| 问题 | 07 文档立场 | 本文档立场 | 最终建议 |
|------|-----------|-----------|----------|
| Crucix 定位 | 实时信号总线（横切） | 实时信号总线 + 统一仪表板基座 | **两者皆是**。Phase 1 纯信号总线，Phase 2 扩展为开阳载体 |
| 开阳物理容器 | macro-scan（天枢） | crucix | **Phase 1 在 macro-scan，Phase 2 迁移到 crucix** |
| :8899 命运 | 保留并扩展 | 降级为管理面板 | **Phase 2 末评估退役/降级** |
| 是否重新设计架构 | 否 | 否 | **07/08/09 主架构不动，仅补充开阳层物理归属** |

**一句话**：07 的架构逻辑层划分是对的，但开阳层的"物理家"应该在 Crucix 容器，不是 macro-scan 容器。Phase 1 按 07 快速验证，Phase 2 把开阳搬进 Crucix。
