## 〇、为什么要做这个对标（回答用户的原问题）

前文已确认：天枢 10 类"死数据"并非纯浪费，而是 prior.yaml 里规划给天璇预测目标的"预采集库存"；但 prior.yaml 已部署却**语法损坏**，且天璇重写未做。这些结论仍困在"自家代码"里——容易把局部合理当全局最优。

## 二、五类成熟方案逐项拆解

### 2.1 地缘冲突早期预警系统（整系统对标：ICEWS / ViEWS / World Tension Meter）

**D1 方法论根基**
- **ICEWS**（DARPA，Lockheed Martin）：混合方法(mixed methods)，组合异构统计模型 + 基于主体的 ABM 模型，聚合准确率 >80%；100+ 数据源、250+ 新闻 feed；核心做法是"近实时供给 + 模型可下钻可视化以建立信任"。
- **ViEWS**（Uppsala/PRIO）：明确"divide and conquer"——把预测拆为子任务(sb/os/ns)再用集成(ensemble)出 forecast；评估用 **AUROC / AUPR / Brier 分数**，且把"模型批评→下代模型"做成迭代闭环(Colaresi & Mahmood 2017)。
- **World Tension Meter**（活例，2026）：每日用 GDELT+ACLED+FRED+商品 API 合成"紧张指数"= 冲突25%·能源20%·贸易20%·金融20%·媒体15% 加权综合；**它显式把"慢结构指标"(油价/VIX/收益率/活跃冲突数)作为"结构风险监视器"单列、每周更新、不进每日分**——这正是天枢 GRV(快变量)与慢变量拆分的直接参照。

**D2 架构分层**
- ICEWS 三件套：iDATA(事件库) → iTRACE(趋势) → iCAST(预测)，层间经由"事件三元组 who-did-what-to-whom"统一语义穿透。
- WTM 明确分层：5 个**日更快信号** + 独立的**周更慢背景上下文**（"这些指标补充 WTM 分数但不并入其中"）。

**D3 权重来源**
- ViEWS 权重来自**统计/ML 模型学习**(logit/动态模拟)，不是人手拍；且有"theme 贡献度"消融实验量化每个变量价值。
- WTM 权重是公开透明的手工设定(25/20/20/20/15)，但**每个权重都附"为什么"的文字论证**（"冲突25%最高，因为战争牵动一切"）。

**D4 绑定层与契约**
- ICEWS 用 CAMEO 事件分类法 + Goldstein 语调分作为"事件→指标"的统一契约，所有源都映射到同一事件本体。

**D5 校验闸门**
- ViEWS：每年 out-of-sample 评估 + 代码/数据全公开可复现；Brier/AUROC 双轨校验防"排序好但概率不准"。

**D6 知识层**
- ICEWS 的 iDATA 本质是**事件知识库**(2500万+ geolocated events)，iSENT 做情感，已是"结构化事件 + 语调"双轨。

> **天枢对应缺口**：天玑 verifier 的 Brier/BSS 方向对，但缺 ViEWS 的"消融/迭代闭环"；GRV 与慢变量的拆分有雏形但无 WTM 那种"慢变量单列不并入"的明确纪律；整体缺 ICEWS 式"可下钻透明"输出。

> **可借用轻量等价物**：①给每个 GRV 维/预测目标权重补一段"为什么"文字论证(学 WTM)；②慢变量严格"单列、不并入日更快变量"(学 WTM 结构监视器)；③天玑验证加"特征消融"步骤(学 ViEWS)。

### 2.2 OECD/UNECE 综合指标方法学（GRV 11维合成的直接对标）

**D1/D3 方法论根基与权重**
- GRV 11 维加权合成，**本质就是 OECD 定义的"综合指标(Composite Indicator)"**。
- OECD/UNECE《Handbook on Constructing Composite Indicators》(2008, Nardo et al.) + JRC 10-Step Guide 规定标准步骤：
  1. **理论框架**(为什么这些维度该合在一起)
  2. **数据选择**(分析合理性、可测性、国家覆盖)
  3. **缺失值插补**
  4. **多元分析**(PCA/因子分析评估结构适切性)
  5. **归一化**(0–1 消除量纲)
  6. **加权**
  7. **聚合**
  8. **敏感性分析**(Monte Carlo 扰动权重看结论稳不稳)
  9. **与其他指标关联**
  10. **可视化**
- **手册头号警告原文**：权重的"任意性(arbitrary nature of the weighting process)"是综合指标最大的坑；"non-aggregators 学派"的根本反对意见正是"加权过程主观"。

**D3 权重来源（关键）**
- OECD 提供多种权重方法：PCA/因子分析(数据驱动)、回归、AHP、公共舆论、**等权**(equal weight 不等于无权重，是"假设同等重要")。
- **信度检验**：Cronbach's α 检查变量是否真在测同一概念（内部一致性）。
- **敏感性分析**：Monte Carlo 扰动权重，看综合结论是否稳健。

**D5 校验闸门**
- OECD 强调"transparency about methods, assumptions and limitations"是强制项；JRC 10步指南明确"先做内部一致性评估，再做不确定性/敏感性分析"。

> **天枢对应缺口**：geo_risk_vector.py 里 GRV 合成权重是**硬编码常量**，prior.yaml 里是**全手写交叉矩阵**——两者都**零理论框架陈述、零归一化说明、零 α 信度检验、零 Monte Carlo 敏感性分析**。**正好踩中 OECD 头号反模式"任意权重"**。

> **可借用轻量等价物**（零基建成本）：①为 GRV 合成补一份"理论框架"短文(哪些维测什么、为何合);②加 Cronbach's α 检验 11 维是否真在测"同一地缘紧张"(若 α 低，说明维度分裂，应拆分而非硬合);③用 Monte Carlo 对权重做 ±20% 扰动，看 composite_grv 结论是否翻转(若翻转，说明当前权重结论脆弱)。这三点纯 Python(numpy/scipy)即可，不需新架构。

### 2.3 特征库与绑定层（Feast + Palantir Ontology）：治 D4 契约先行 + D2 分层

**D2/D4 架构分层与绑定层**
- **Feast（开源特征库）**核心抽象：Entity / DataSource / FeatureView / FeatureService。
  - 关键：**特征定义为代码+schema**；`get_historical_features` 用 **point-in-time join** 防未来值泄漏；**训练/推理用同一套特征定义**(单一真相源)，根除 training-serving skew。
  - FeatureService = "把若干 feature view 打包成稳定契约供模型消费"，**将模型输入清单与底层存储布局解耦**。
- **Palantir Ontology** 三层模型：
  - **语义层**(Object Type/Property/Link Type)：定义世界"名词"
  - **动力层**(Action/Function)：把原始源 **hydration 水合**进对象 + **完整数据血缘**
  - **动态层**：实时血缘、安全、可操作
  - 最值钱的一点：**原始数据 → 语义对象 → 可执行操作，三层之间靠显式、可审计的绑定(Link Type)连接**。

**D1 方法论根基**
- Feast 的 point-in-time correctness 本质是"时间维度上的契约"——保证训练时拿到的特征 = 标签发生时刻已知的真实特征，不是今天看到的。

**D5 校验闸门**
- Feast 的 `feast apply` 把特征定义注册到 Registry 并做版本控制；schema mismatch 在构建期就报错，不可能"部署了但加载不了"。

> **天枢对应缺口**：天枢的"源→表征(GRV)→目标(预测)"绑定**藏在 prior.yaml 一张手写表里**，该表既损坏又无 schema 校验；没有任何"契约先行"——fetcher 产出字段与未来消费端期望字段从未对齐。这正是 D4 缺失的典型。

> **可借用轻量等价物**：①把 prior.yaml 的"源×目标"映射抽成**独立的、带 schema 的绑定模块**(类似 Feast 的 FeatureService/ Ontology 的 Link Type)，而非塞进权重矩阵;②给每个 fetcher 定义"产出字段契约"(Pydantic model)，消费端按契约取数;③"契约先行"——新增源时先定契约再写采集，避免囤错形状的数据(治 doc00 T1-1 孤儿源隐患)。

### 2.4 配置防腐与校验闸门（dbt / Pydantic·Pandera / Great Expectations / Data Mesh）：治 D5

**D5 校验闸门（核心）**
- **dbt tests**：断言写在 YAML 里、和模型同仓库、随 `dbt test` 失败即阻断下游——"测试即代码、版本化、就近关联"。
- **Pydantic**：记录级 schema 校验，声明模型后自动拒收非法记录，报错结构化。
- **Pandera**：DataFrame 级 schema 校验，可在 transform 前后 `@check_input/@check_output` 双端把关。
- **Great Expectations**：expectation suite + checkpoint + Data Docs(HTML 报告)，适合企业级质量门禁。
- 共同范式：**Data Contract(数据契约)** 先行——写明必填列/类型/可接受范围/唯一性/SLA，机器自动校验。

**D2 架构分层**
- **Data Mesh** 理念：按域(domain)模块化 ownership，每个域自治其数据产品——对应"巨型单一 YAML 应拆成 per-target 小文件"。

**D3 权重来源**
- 校验闸门不解决权重合理性，但能**保证权重文件至少能被加载**(这是 prior.yaml 当前都没做到的底线)。

> **天枢对应缺口**：prior.yaml 是 **~65 目标 × ~27 源的巨型手写交叉矩阵，无 schema、无校验、无测试**——它已经崩过一次(内联多键格式错误)，修好也必然继续腐化。调度器 08-01 三个月度 job 会因它解析失败集体报错。这正是 D5 缺失的教科书案例：配置正确性靠"人谨慎"而非"机器守门"。

> **可借用轻量等价物**（极低成本）：①prior.yaml 加载前加一道 `yaml.safe_load` + 维度完整性断言的**启动自检**(doc20 P1 方案A);②按目标拆成 per-target 小文件(学 Data Mesh)，缩短编辑面;③给每个源/目标的字段加 Pydantic schema，fetcher 产出即校验;④任何 config 落地前必须"机器加载成功"才算 done(学 dbt 的 fail-loud 文化)。

### 2.5 知识层（Microsoft GraphRAG + GDELT GKG）：治 D6

**D6 知识层**
- **Microsoft GraphRAG**(Edge et al., 2024)：LLM 从非结构化文本自动抽取实体/关系→建 KG→Leiden 社区检测→分层社区摘要→ Global/Local/Drift 三种查询。全局问题回答能力比传统向量 RAG 高 50–70%。
- **GDELT GKG**：GDELT 自称 Global Knowledge Graph，但本质是多表关系库；2025 论文《Talking to GDELT Through Knowledge Graphs》指出**必须按其本体(ontology)把关系表正确实现为 KG** 才能用于 QA。
- **关键警告**（那篇论文 + dreaming.press 的 EDC 框架）：
  1. **LLM 产 KG 易"star-shaped 退化"**(单中心节点 + 全连，无其它边)——除非用**本体约束抽取**(schema-guided extraction)。
  2. **实体解析(entity resolution)是质量决定步骤**：per-chunk 抽取会把 "OpenAI"/"OpenAI Inc."/"the company" 拆成 3 个节点，必须 canonicalize 合并。
  3. 本体驱动 KG + 向量库**双轨优于任一方**。

**D2 架构分层**
- GraphRAG 的"图构建 → 社区检测 → 社区摘要"是把知识结构化后再供检索，对应天枢 narrative_processor 该有的"叙事→结构化"流程。

**D4 绑定层与契约**
- 本体(ontology)本身就是一种"契约"——限定实体/关系类型，保证图可查询。

> **天枢对应缺口**：narrative_processor / tianji_db(reasoning_trace) 本质是 JSON 堆，无本体约束，LLM 抽取未受 schema 限制，未做实体解析，也无"KG+向量双轨"。tianji_db 的 reasoning_trace 很有价值但缺结构化。

> **可借用轻量等价物**：①给叙事/推理轨迹定义**本体(schema-guided)**：限定实体类型(事件/人物/组织/地点/引述)与关系类型，约束 LLM 抽取;②加**实体解析**步骤(canonicalize 合并同名实体);③叙事桶用"本体 KG + 向量库"双轨存(不必上 Neo4j，networkx + 现有 chroma_db 即可);④学 GraphRAG 的"社区检测+分层摘要"做 daily_narrative 的结构化。

## 五、给天枢的方案层建议（非代码改动，待用户决策）

**原则**：转移的是**模式**不是企业平台。个人 NAS 研究系统不宜为学 Palantir 去搭 Neo4j 集群——用 networkx/GraphRAG/Pydantic/numpy 的轻量等价物即可。同时谨记 ViEWS 的教训："少而强的几个变量 ≈ 复杂模型"，天枢当前 7 层 + prior.yaml 65×27，**可能已偏重**，回头审视是否过度工程。

**建议优先级**：

1. **🔴 立即(防炸)**：prior.yaml 启动自检 + per-target 拆分（治 D5/P0）。这是 doc20 已审出的 P1，纯配置文件修复，零架构风险。
