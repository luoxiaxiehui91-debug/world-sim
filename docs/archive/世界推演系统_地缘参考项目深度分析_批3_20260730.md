## 〇、结论先行（给实施 session 的 TL;DR）

1. **B6 OECD 综合指标 10 步法** —— GRV 11 维加权合成**本质就是 OECD 定义的 Composite Indicator**。它的头号警告「权重的任意性（arbitrary nature of weighting）」**正好命中我们 GRV 硬编码常量 + prior.yaml 手写矩阵**这一最大反模式。可立即借用的外壳：**理论框架短文 + 归一化说明 + Cronbach's α 信度 + Monte Carlo 敏感性**——零基建、纯文档+轻量 numpy，先把「为什么这么加权」说清楚。
2. **B7 Feast 特征库** —— 核心价值是 **point-in-time join（时间点正确连接）** 防训练未来泄漏 + **单一真相源**保证训练/服务一致。直接对标我们的 **M6 vintage/point-in-time** 纪律与 D2/D4 绑定层。我们不需要部署 Feast 集群，但要借它的**模式**：每个源按 `entity + timestamp` 定义、回溯测试用时间点连接、特征契约单一来源。
3. **B8 Palantir Ontology** —— 最值钱的一句：**原始数据→语义对象→可执行操作，靠显式可审计的 Link Type 连接**。我们的 prior.yaml 65×27 手写绑定矩阵正是它要治的反面（spaghetti join）。借它的**类型化本体（Object/Property/Link）+ 完整血缘**，把「源→信号→目标」从一张脆表改成可审计的图。
4. **B9 dbt** —— 「**Data Contract 先行 + fail-loud 测试闸门 + 自动 lineage**」是 prior.yaml 曾崩坏那类问题的对症药。借它的**模式**：每个 fetcher 产出写 YAML 断言（not_null / accepted_values / 关系），校验失败即阻断下游，并自动生成依赖 DAG。这是治 D5 的零/低基建等价物。
5. **B10 Microsoft GraphRAG** —— LLM 抽取**类型化实体/关系**→建 KG→**Leiden 分层社区检测**→自底向上社区摘要→Global/Local/DRIFT 三模式查询。直接对标我们 **L5 叙事归因（narrative_processor 11 维）/ D6 知识层**。关键教训：**本体约束抽取（防 star-shaped 退化）+ 实体解析 canonicalize** 是质量决定步骤；**KG + 向量双轨优于任一方**。

> 五者组合 = 我们「数据层（M6/M7）+ 绑定层（D2/D4）+ 校验闸门（D5）+ 知识/叙事层（L5/D6）」的完整方法论补齐链。与 Batch 1/2 的「事件编码（ICEWS/GDELT）+ 冲突预测校准（ViEWS/UCDP）」形成「信号→合成→绑定→校验→叙事」全栈参照。

## 一、B6 · OECD 综合指标方法学（Composite Indicators）

### 1.1 它解决什么
GRV 11 维加权合成、世界经济论坛全球竞争力、联合国 HDI、欧盟创新记分牌……本质都是 OECD/JRC 定义的 **综合指标（Composite Indicator, CI）**：把多个单维指标压缩成一个可比的总分。OECD 的《Handbook on Constructing Composite Indicators》(Nardo et al. 2008, EUR 21682 EN) 与 JRC 10-Step Guide 是这一领域的权威方法论标尺，也是**批评与防坑**的权威来源。

### 1.2 方法论（一手来源：Nardo et al. 2008；JRC 10-Step Guide；UNECE Ch.4）
**10 步标准流程：**
1. **理论框架（Theory/Conceptual framework）**：先定义「这个指标到底测什么」、各子指标与总构念的理论关系。*这一步我们完全缺失。*
2. **数据选择**：单变量描述统计、缺失分析、剔除不相关数据。
3. **缺失值插补（Imputation）**：均值/回归/EM 算法补全。
4. **多元分析（Multivariate analysis）**：用相关/PCA 检查子指标是否测同一底层现象（防止重复计量）。
5. **归一化（Normalization）**：把量纲不同的指标拉到同一尺度。最常用 **min-max**：
   `x'_i = (x_i − min(x)) / (max(x) − min(x))` → 落在 [0,1]。
   也可用 z-score、log、distance-to-target。
6. **加权与聚合（Weighting & Aggregation）**：权重反映相对重要性，总分
   `CI = Σ_i  w_i · x'_i`，其中 `w_i = 1/k` 即**等权（equal weight）**。
   - **关键语义**：等权 ≠ 无权重。等权是「假设所有子指标同等重要」这一**明确假设**，仍是一个有含义的加权方案；「无权重」在方法学上不成立。
   - 权重方法：等权 / PCA / 因子分析 / 回归 / AHP（层次分析法）/ 公共舆论 / 预算分配。
7. **敏感性分析（Sensitivity & Robustness）**：**Monte Carlo 扰动**——随机扰动权重与输入，看排名/分级是否稳定。这是 CI 可信度的核心。
8. **回到多元分析**：用扰动后结果再检验构念一致性。
9. **与其他变量关联（External validation）**：与独立外部指标对照。
10. **可视化与发布**：透明展示权重、归一化、不确定性。

**信度检验（一手公式）——Cronbach's α**（内部一致性）：
`α = (k / (k − 1)) · (1 − Σσ_i² / σ_total²)`
其中 `k` = 子指标数，`σ_i²` = 第 i 项方差，`σ_total²` = 总分方差。`α > 0.7` 一般视为可接受的内部一致性。GRV 11 维若彼此高度相关，α 会偏高（冗余）；若彼此独立，α 偏低（不是同一构念）——α 能提示「11 维是否真在测同一件事」。

### 1.3 已知局限（决定我们「怎么用」而非「照搬」）
- **头号警告（原话）**：权重的「**任意性（arbitrary nature）**」是综合指标最大坑；「**non-aggregators 学派**」的根本反对意见正是「加权过程主观、不可证伪」。任何 CI 都必须**公开并论证权重来源**，否则只是作者的主观编号。
- 归一化方法改变排名（min-max 对极值敏感，z-score 对异常值敏感）——必须注明并做敏感性。
- 子指标相关会虚高总分区分度（PCA/α 可侦测）。
- 步骤多、易沦为「为合成而合成」；方法学仪式感不等于预测力。

### 1.4 映射到我们 L 哪层
- **GRV 合成（L1 状态 / L3 预警状态）**：GRV 11 维加权 = 一个 Composite Indicator。对标 doc §2.2 已点明我们「**正好踩中 OECD 头号反模式『任意权重』**」——geo_risk_vector.py 硬编码常量 + prior.yaml 手写矩阵，**零理论框架、零归一化说明、零 α 信度、零 Monte Carlo**。
- **M6/M7 数据层上游**：权重两处存储混淆（GRV 硬编码 vs prior.yaml）对应 OECD「等权≠无权重」的清晰语义缺失（对标 doc D2/D3）。

### 1.5 后续可借用点（非代码）
- **补三件套外壳（零基建）**：① 写 1 页理论框架短文「GRV 测的是『地缘宏观风险态势』，11 维分别覆盖…」；② 文档化归一化方法（min-max 公式 + 为何选它）；③ 加 **Cronbach's α** 与 **Monte Carlo 敏感性**（轻量 numpy 随机扰动权重 1000 次，看分级稳定性）——直接治 D1/D3。
- **显式定义两类权重语义**：L1 状态合成权重 vs L2 目标归因权重，各自单一真相源，禁止混用（对标 doc D3）。
- **等权基线**：先跑「等权 GRV」作为对照基线，再叠加先验权重，使权重差异可论证而非黑箱。

## 二、B7 · Feast（特征库 / Feature Store）

### 2.1 它解决什么
ML 工程的核心痛点：**训练/服务不一致（training-serving skew）** 与 **未来数据泄漏（data leakage）**。Feast 是一个开源特征库，让「离线训练」和「在线服务」用**同一套特征定义**，并在回溯构造训练集时严格按时间点取数。

### 2.2 方法论（一手来源：docs.feast.dev；marovi.ai；youngju.dev；对标 doc §2.3）
**核心抽象：**
- **Entity（实体）**：连接键，如 `entity_id` + `event_timestamp`。
- **DataSource（数据源）**：原始数据来自哪（文件 / BigQuery / Kafka…）。
- **FeatureView（特征视图）**：从一或多个 DataSource 计算特征的逻辑分组，按 `entity + timestamp` 索引。
- **FeatureService（特征服务）**：为某个模型/目标绑定的 FeatureView 命名集合——即「**哪些特征喂哪个目标**」的契约。

**最值钱的两点：**
1. **Point-in-time join（时间点正确连接）**：`get_historical_features(entity_df, features)` 对 entity_df 中**每一行的 timestamp**，只连接「在该时间戳**之前**有效」的特征值——绝不拿未来值。这是防泄漏的关键：`training_set = join(label_row.timestamp → latest_feature_valid_at_or_before_timestamp)`。
2. **单一真相源 + 版本化注册**：`feast apply` 把特征定义注册进 **Registry（版本化）**，schema mismatch 在构建期就报错；训练与服务共用同一 FeatureView → 零 skew。

**配套**：`materialize` 把最新特征值推到在线库（Redis）供低延迟服务。

### 2.3 已知局限
- 重基建：Registry/在线库/批处理需运维，个人研究系统不必全上。
- 它管「特征定义与取数」，不管「权重怎么合成」「信号怎么解释」——后者仍归我们。
- 概念漂移需手动重训/重定义 FeatureView。

### 2.4 映射到我们 L 哪层
- **M6 vintage / point-in-time（直接对标）**：我们的 ALFRED 式 vintage、回溯测试（用历史 GRV 校验天璇预测）都要求「取数时间点正确」——Feast 的 point-in-time join 正是 **M6 纪律的教科书实现**。
- **D2/D4 绑定层**：prior.yaml 的「源→GRV→目标」是 65×27 手写矩阵、曾崩坏、无契约。Feast 的 **FeatureService = 带 schema 的可测试绑定契约**，正治此缺口。

### 2.5 后续可借用点（非代码）
- **借模式不借平台**：不部署 Feast，但强制 (a) 每个源/fetcher 产出带 `entity + timestamp` 的规整表；(b) 回溯测试统一走 **point-in-time join**（用 pandas `merge_asof` 即可实现），防未来泄漏；(c) 一个 `feature_registry`（轻量 YAML/JSON）作为绑定契约单一来源，替代 prior.yaml 巨表。
- **契约先行**：fetcher 字段契约用 Pydantic 定义（对标 doc 已提），变更即校验。

## 三、B8 · Palantir Ontology（本体语义层）

### 3.1 它解决什么
企业数据散落各处、join 成 spaghetti、决策不可追溯。Palantir Foundry 的 **Ontology（本体）** 把「真实世界」建模成一套**类型化对象 + 显式可审计关系**，并在其上挂载可执行动作，使每一个决策都能追溯到「哪些数据、哪条关系、哪个动作」。

### 3.2 方法论（一手来源：palantir.com/docs/foundry/ontology；53ai.com；对标 doc §2.3）
**三层结构：**
1. **语义层（Semantic）**：`Object Type`（真实实体，如 Sensor/Region/Company）、`Property Type`（属性）、`Link Type`（**对象间的显式、类型化、可审计关系**）。本体 = 真实世界的数字孪生。
2. **动力层（Dynamic）**：`Action`（用户可触发、读写对象、带校验/hydration 的操作）、`Function`（可复用逻辑）。两者都跑在 Ontology 上，且带**完整血缘（lineage）**——你能看到哪个 Action 改了哪个对象。
3. **动态/实时层**：对象级安全（每个 Action 按权限校验）+ 实时更新。

**最值钱的一句**：**原始数据 → 语义对象 → 可执行操作，靠显式可审计的 Link Type 连接**。没有脆弱的隐式 join，本体是唯一概念模型；决策可追溯（哪条数据、哪条 link、哪个 action 产出结论）。

### 3.3 已知局限
- 企业级平台，重部署、强绑定 Palantir 生态，个人系统不可直接采用。
- 本体建模本身需要领域专家投入，过度建模也会僵化。
- 价值在「复杂、多源、需审计」的场景；简单管道上它是杀鸡牛刀。

### 3.4 映射到我们 L 哪层
- **D2/D4 绑定层 + L4 结构/Agent**：prior.yaml 那张 65×27 手写矩阵就是 Palantir 要治的反面——隐式、脆、无审计。借它的**类型化 Ontology**：`Object = Source/Signal/Event/Narrative/Region/Target`，`Link Type = feeds / triggers / validated_by`（每条带 provenance）。这给天玑 verifier 提供「哪个源贡献了哪个预测」的可追溯链路。
- **L5 叙事归因**：narrative_processor 的 11 维桶若建模成 Ontology 上的 typed nodes + links，比自由 JSON 更易被 Agent 消费与推理。

### 3.5 后续可借用点（非代码）
- **类型化本体 schema（轻量）**：用 networkx + 一个显式 schema 字典（节点类型/边类型/约束）替代 prior.yaml 巨表；每条「源→目标」关系是一个带 provenance 的 Link，而非矩阵单元格。
- **血缘可审计**：天玑推理溯源（reasoning_trace）升级为「边级 provenance」——每个预测能展开「由哪条 link、哪些源对象推出」。
- **原则（对标 doc §九）**：转移模式不转移企业平台，用 networkx/GraphRAG/Pydantic 轻量等价物即可。

## 四、B9 · dbt（数据转换测试 + lineage）

### 4.1 它解决什么
数据管道「中间表默默坏掉、下游全错、无人察觉」。dbt 让数据转换带**测试闸门**与**自动血缘**，把「Data Contract 先行」落到工程纪律。

### 4.2 方法论（一手来源：docs.getdbt.com；对标 doc §2.4）
- **Models**：SQL/Python 转换（SELECT）→ 物化表/视图。
- **Tests（断言）**：写在 YAML 里，随 `dbt test` 运行；失败即**阻断下游（fail-loud）**。内置：`unique` / `not_null` / `accepted_values` / `relationships`（外键），并支持自定义。
- **Data Contract 先行**：先定义期望（schema/约束），再建转换——非法数据在入口被拒。
- **Lineage（血缘）**：dbt 通过 `ref()` 自动构建模型依赖 DAG，可可视化「改一个源会波及什么」。
- **Docs**：从 schema + description 自动生成文档。
- **Data Mesh**：按域模块化 ownership——对应「巨型单一 YAML 应拆成 per-target 小文件」。

**同族范式**：Pydantic（记录级 schema 校验自动拒收非法）、Pandera（DataFrame 级 `@check_input/@check_output` 双端把关）、Great Expectations（expectation suite + checkpoint + Data Docs）。共同信条：**Data Contract 先行 + 失败即阻断**。

### 4.3 已知局限
- 面向数据仓库（Snowflake/BigQuery），我们 CSV/JSON 管道需等价轻量化。
- YAML 断言仍需人写，覆盖不全仍会漏。
- 不改「算什么」，只管「数据干净/契约守约」。

### 4.4 映射到我们 L 哪层
- **D5（校验闸门）**：prior.yaml 曾语法损坏、无 schema/无测试，靠运行路径绕开（非 P0 但必继续腐化）。dbt 的 fail-loud + 启动自检正是治此。
- **M7 干净数据层（FXMacroData 范式）**：M7 强调「agent 友好的干净数据接口」，dbt 的契约+测试是「干净」的工程保障。

### 4.5 后续可借用点（非代码）
- **轻量 fail-loud 闸门**：每个 fetcher 产出后跑一组 Pydantic/YAML 断言（关键字段 `not_null`、枚举字段 `accepted_values` 如 `type_of_violence ∈ {1,2,3}`、关系完整性）；失败即终止当日 pipeline 并告警（ntfy），不再「坏数据静默进 GRV」。
- **启动自检**：加载 prior.yaml/契约前 `safe_load` + 维度断言；per-target 拆分（治 D5，对标 doc §八/§九）。
- **自动 lineage**：用依赖声明生成「源→GRV→契约→macro-sim」DAG，源变更影响一目了然。

## 五、B10 · Microsoft GraphRAG（图谱增强检索）

### 5.1 它解决什么
传统向量 RAG 擅长单跳检索，但**全局性、多跳、跨文档的「整体性问题」**（如「过去一年各冲突区的叙事主题如何演变？」）答不好。GraphRAG(Edge et al. 2024, arXiv 2404.16130) 用 LLM 从语料抽取**实体/关系建知识图谱**，再做**分层社区摘要**，显著增强全局推理。

### 5.2 方法论（一手来源：Microsoft GraphRAG 论文/博客；vectoringai；kindatechnical；marovi.ai；对标 doc §2.5）
**管线：**
1. **文档 → 文本分块**。
2. **LLM 抽取实体 + 类型化关系** → 构建**类型化多重图（typed multigraph, KG）**。
3. **Leiden 分层社区检测**：优化模块度（modularity）把图分成**层级化社区**（从叶子到根）。
4. **自底向上社区摘要**：先摘要叶子社区，再用子社区摘要去摘要父社区 → 生成各级「community reports」。
5. **查询模式**：
   - **Global（全局）**：对所有 community reports 做 map-reduce，适合全局/整体性问题。
   - **Local（局部）**：取实体 + 邻居子图 + 社区摘要做检索，适合具体实体问题。
   - **DRIFT**：混合模式，用社区结构路由。

**关键数字（带 caveat）**：Microsoft 自评——在 *global sensemaking* 问题上 GraphRAG(global) 比 vanilla RAG 高数十个百分点（其 Podcast/Mix-set 基准 +70%+）。但**独立复现分析**指出：若 KG 抽取**无本体约束**，易「**star-shaped 退化**」（单中心全连），多跳精度可**跌到 45–50%**，反低于调好的向量 RAG（约 80–85%）。两条质量决定经验：
- **实体解析（Entity Resolution / canonicalization）**：`"OpenAI"`/`"OpenAI Inc."`/`"the company"` 必须合并为同一规范实体——这是 KG 质量的决定性步骤。
- **本体约束抽取**：边必须是预定义类型，否则退化成星型废图。

### 5.3 已知局限
- 抽取成本随语料线性增长（每次 LLM 调用）。
- 依赖抽取质量；本体/实体解析没做好，整体崩。
- 社区摘要可能引入幻觉（摘要本身由 LLM 生成）。
- **双轨最优**：本体驱动 KG + 向量库并用，优于任一单用（对标 doc §2.5 已记）。

### 5.4 映射到我们 L 哪层
- **L5 叙事归因 / D6 知识层**：narrative_processor 11 维叙事桶、tianji_db 的 reasoning_trace 本质是「JSON 堆」——无本体约束、未实体解析、无双轨（对标 doc §2.5 缺口）。GraphRAG 的**类型化抽取 + 实体解析 + 社区摘要 + KG/向量双轨**是直接解法。
- **与 GDELT GKG 协同**：GKG 本就是带 V2Themes/V2Locations/GCAM 的半结构化 KG，须按本体正确实现为 KG 才能用于 QA（对标 doc 原话）。

### 5.5 后续可借用点（非代码）
- **定本体 schema**：先写「叙事实体类型（Actor/Region/Event/Theme）+ 关系类型（triggers/feeds/validated_by）」，再让 LLM 按 schema 抽取，防 star-shaped 退化。
- **实体解析 canonicalize**：抽取后跑归一化（同义词表/embedding 近邻合并），把「同一行为体」并成一个规范节点。
- **社区摘要喂 11 维桶**：用 Leiden 社区检测自动生成「叙事主题」，作为 narrative_processor 11 维桶的**数据驱动种子**，而非纯手工设定。
- **KG + 向量双轨**：networkx 存 KG、chroma 存向量，查询时按问题类型路由（对标 doc 结论）。
