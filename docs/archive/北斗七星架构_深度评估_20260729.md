```

                                          ↓
                                        天玑(验证)
                                          ↓
                                       玉衡(校准)
                                          ↓
                                       摇光(进化)
```

## 二、发现的 4 个问题

### 🔴 问题 1：玉衡位置违反数据流

原方案把"玉衡（校准）"放在数据流中段，但实际：

- **校准参数的写回对象**是天枢（GRV 权重）和天璇（agents.yaml）
- 这是**反向闭环**（验证→校准→观测/仿真），不是正向流水线的一环
- 玉衡应该是**独立的横跨服务**，不是中间节点

### 🟠 问题 2：天权职能模糊

"基于天玑验证 + 天璇推演 → 自动生成行动建议（对冲方案、仓位调整、预警等级提降）"

两个不同功能被合并：
- **战术决策**（基于天璇路径 → 情景应对预案）
- **预警分级**（基于天玑准确率 → 报告可信度标注）

这是两个不同循环，合并在一个"天权"里会变重。

### 🟡 问题 3：摇光是横切层，不该在流水线末端

"自我诊断、异常检测、自动 rollback、知识图谱"——这些都是**横向基础设施**，任何模块都可能崩溃需要 rollback，不是流水线末端的后处理。

### 🟡 问题 4：开阳定义偏弱但维护负担不小

ntfy 推送、Web UI（8899）、API 开放——已经在 macro-scan 里实现了。独立成"开阳"会变成纯抽象层，工作量不大但增加"维护多个代码库"负担。

## 四、根本问题：功能分层 vs 流水线分层混淆

原方案把"功能维度"的 7 个抽象层当成了"流水线"，但实际工程上是：

```
正向数据流：观测 → 仿真 → 综合 → 发布
反馈流    ：验证 → 校准 → 写回观测/仿真
横切层    ：自主运维（异常检测/rollback/知识图谱）
```

**反馈流和横切层不应该跟数据流混在一条线上**。否则部署会很乱——比如玉衡什么时候跑？每个周期末？它属于天玑调度里的事，不是流水线一环。

---

## 五、修正建议

### 方案 A：调整顺序 + 重新对齐职责

```
【正向数据流】
天枢(观测) → 天璇(仿真) → 天权(分析综合/决策) → 开阳(呈现/发布) → 用户
                       ↓
                     天玑(验证打分)
                       ↓
【反向校准流】
                     玉衡(参数校准) → 写回天枢/天璇
                       ↓
【横切基础设施】
                     摇光(自主运维/监控/rollback)
```

具体变化：
- **天权** 改为"分析综合中枢"——不再叫决策层，是把仿真+观测+假设推演综合成可操作建议
- **玉衡** 明确为"反向通道"——独立服务，不在流水线
- **开阳** 直接定义为"呈现与发布层"
- **摇光** 作为"横切运维层"——类似 SRE，做监控/报警/rollback

### 方案 B：只做 3 星，后四星增量定义

天枢/天璇/天玑已有设计稿（2 运行 + 1 DRAFT），**后四星目前没有任何代码、PRD、时间线**。

过早设计"完美 7 星"会：
1. 团队陷入画大饼
2. 增加未来路径依赖——一旦命名"摇光是自主进化"，未来发现该叫"故障应急"就难改名
3. 命名成本 > 实际收益

**建议**：
- 保留 7 星命名愿景作为**北极星**
- 但**不立刻写设计文档**
- 等天玑 V1（2026-09-30 计划）跑起来后，根据反馈**增量定义**第四星
