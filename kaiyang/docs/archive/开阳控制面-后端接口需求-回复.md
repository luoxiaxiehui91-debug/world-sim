## 二、通用 · 操作状态轮询（2.1）

### 2.1.1 状态端点现在有吗？

**没有**。但 A3a 设计有 E7 `GET /control/operations/{id}`。返回结构和开阳的 2.1 建议高度一致，有两个差异需要注意：

**差异一：状态机补一个 `queued` 态**

开阳提的状态机是 `accepted → running → completed/failed`。实际上天枢操作不一定是即时执行的——命令写到 `replay_queue/` 后，scheduler 最多 30s（D2-2 定的轮询周期）才消费到。这 30s 里需要一个 `queued` 态来区分"还没开始排队"和"正在执行"。

完整状态机：

```
accepted → queued → running → completed
                            → failed
```

- `accepted`：指令已通过鉴权+校验，已写入队列
- `queued`：在队列中等待 scheduler 消费（预计 ≤30s）
- `running`：scheduler 已取走并正在执行
- `completed` / `failed`：终态

### 2.1.2 SSE vs 轮询？

**本期轮询**。A3a 设计里 scheduler 本身就是轮询模型（30s），操作状态轮询同理。SSE 推后到 Wave 2。轮询间隔建议 2-5 秒（操作大多数是秒级完成的，30s 是队列等待上限）。

### 建议返回格式对齐

```json
{
  "operation_id": "op_abc123",
  "command_id": "cmd-550e8400",          // 新增：对应的命令信封 ID
  "idempotency_key": "uuid-v4",          // 新增：幂等去重键
  "type": "fetcher_rerun",
  "status": "accepted | queued | running | completed | failed",
  "progress": 0,
  "progress_message": "已进入执行队列，等待调度器消费...",
  "affected_fetchers": ["fred_v1"],       // 新增：受影响的 fetcher（方便前端更新局部状态）
  "result": null,
  "error": null,
  "created_at": "2026-08-01T00:00:00Z",
  "completed_at": null
}
```

## 三、天枢运维（macro-scan）

### 3.1 获取 fetcher 列表

**没有现成接口。**

A3a 设计 E6 `GET /control/fetchers` 已规划。开阳所需的字段（id/name/status/interval/last_run/last_status）可以全量满足——但有几个关键设计决策需要对齐：

**(a) 真相源**：fetcher 状态从 `jobs.state.yaml`（外置控制面，D2 已决）+ `observability.py` 的心跳文件中综合判断。如果一个来源说"running"另一个说"unkown"，以 scheduler 实际运行状态为准。

**(b) 频率格式**：不是 `interval_seconds`。调度表达式是 `I15`（每15分钟）、`dom=1`（每月1号）、`cron 30 5 * * *`（每天5:30）。详见下文 3.4。

**(c) ID 格式**：不是 `gdelt_v1` 这样的自创 ID。fetcher id 直接用模块名（即 `fetch_earthquake` / `fetch_fred_history` 等），和 scheduler 的 JOBS 数组一一对应，不需要额外维护 ID 映射。

建议返回格式：

```json
{
  "fetchers": [
    {
      "id": "fetch_earthquake",
      "name": "地震采集（USGS 实时）",
      "status": "running",
      "schedule": "I15",
      "last_run_at": "2026-07-31T13:00:00Z",
      "last_status": "success",
      "next_run_at": "2026-07-31T13:15:00Z",
      "enabled": true                  // 暂停/恢复状态
    }
  ]
}
```

### 3.2 重跑 fetcher

**没有现成 API。** A3a 设计 REPLAY_FETCHER 命令。

协议要点：

**(a) 命令入口**：开阳可以用 RESTful 风格端点，后端内部转命令信封。建议端点：

```
POST /api/v1/control/fetchers/rerun
Body: {
  "fetcher_ids": ["fetch_earthquake", "fetch_fred_history"],
  "idempotency_key": "uuid-v4"        // 必需：防止手滑重复触发
}
Response 202: {
  "operation_id": "op_abc123",
  "status": "accepted",
  "affected_fetchers": ["fetch_earthquake", "fetch_fred_history"]
}
```

**(b) 幂等**：同一个 `idempotency_key` 24 小时内重复提交，直接返回首次结果，不做二次执行。

**(c) 执行机制**：重跑请求写成票据落 `replay_queue/` 目录（目录挂载，不是单文件），scheduler 轮询取票执行。并发上限 = 3（D2-6 已决），超过的排队。

**(d) 操作追踪**：返回 `operation_id`，前端轮询 2.1 的状态端点获取进度。

### 3.3 暂停 / 恢复 fetcher

**没有现成 API。** 建议端点：

```
POST /api/v1/control/fetchers/{fetcher_id}/pause
POST /api/v1/control/fetchers/{fetcher_id}/resume
```

- 暂停：写 `jobs.state.yaml` 的 `enabled=false`（带可选 `paused_until` 自动恢复时间）。scheduler 30s 轮询后生效。
- 恢复：写 `enabled=true`，清 `paused_until`。
- 操作走同一套鉴权+审计路径。

### 3.4 调整采集频率

**没有现成 API。** 这是最需要对齐协议的端点。

**(a) 频率表达不是 `interval_seconds`**

开阳文档里写的 `{"interval_seconds": 7200}` 不够——天枢的调度不是纯秒数：
- `I15` = 每 15 分钟触发（按分钟取模，桶去重）
- `dom=1` = 每月 1 号
- `cron 0 9 * * *` = 每天 09:00

**建议方案**：前后端一起用一个 `schedule` 字符串字段，值域由**动态接口**提供（避免耦合）：

```
GET /api/v1/control/fetchers/{fetcher_id}/allowed-schedules
Response 200: {
  "current": "I15",
  "options": [
    {"label": "每15分钟", "value": "I15", "description": "≤50% 安全水位"},
    {"label": "每小时", "value": "I60", "description": "≤50% 安全水位"}
  ]
}
```

调频时前端传回选取的 `value`：

```
PUT /api/v1/control/fetchers/{fetcher_id}/schedule
Body: { "schedule": "I15" }
```

这样不管后端怎么改表达式规则，前端只跟 API 返回的可选项走，永远不会错位。

**(b) 调频校验（后端内部，前端没有传参义务）**

服务端四道校验任一不过即 reject，返回 400 + 明确的拒绝原因（如"fetch_news 属日档且 apiKey ~100/日，提频将破限，拒绝"）。规则锚定 `采集频率矩阵.md` 里的安全水位（≤50%）和不更变原则。

**(c) 生效时间**：scheduler 轮询（30s）后新频率生效。调频不改源码，不需要 restart。

## 九、协议级约定（通用，适用于全部端点）

### 9.1 错误响应格式

开阳文档只写了 200/202 的 happy path。后端会统一错误格式：

```json
{
  "error": {
    "code": "VALIDATION_ERROR | AUTHENTICATION_ERROR | NOT_FOUND | RATE_LIMIT | INTERNAL_ERROR",
    "message": "人类可读的错误描述",
    "details": { ... }                     // 可选：具体违规字段
  }
}
```

| HTTP 状态码 | 含义 |
|:--|:--|
| 200 | 查询类成功 |
| 202 | 操作类已受理 |
| 400 | 参数校验失败（含调频审核不通过——返回具体原因） |
| 401 | 未提供有效 Bearer Token |
| 403 | Token 有效但权限不足（如 operator 调用 SET_FREQUENCY） |
| 404 | fetcher/operation 不存在 |
| 429 | 请求频率超限 |
| 500 | 内部错误 |

### 9.2 分页

天枢 24 个 fetcher 不分页。等天玑/玉衡有大数据量场景时再加 `page/limit/total` 字段。本期所有列表端点均为一次性全量返回。

### 9.3 CORS

天枢控制 API 启动时会加 CORS 中间件，只放行开阳的 origin。

### 9.4 跨容器文件契约

全部控制面状态文件（`jobs.state.yaml` / `replay_queue/` / 审计日志 / 未来 sim_trigger）统一使用**目录挂载 + 目录内文件操作**，禁止任何单文件 bind mount + `os.replace()` 原子写（会导致 inode 静默断链，P0 级坑）。这是后端架构铁律，前端不需要关心，只作记录。
